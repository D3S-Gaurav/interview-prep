The target level, using a load balancer as the example

Weak answer: "A load balancer distributes incoming requests across multiple servers."

Strong answer:

  1. The client resolves the service name through DNS to the load balancer's address (often a virtual IP or anycast address) and opens a TCP connection to it.
  2. The load balancer accepts the connection. An L4 balancer decides from the IP and port alone and forwards the packets. An L7 balancer terminates TCP (and usually TLS), parses the HTTP request and can route on path, headers or cookies.
  3. It picks a backend with a policy such as round robin, least connections or a hash, choosing only among backends currently marked healthy.
  4. It forwards the request, often over a pooled keep-alive connection to that backend, and relays the response back to the client.
  5. Health checks (active probes, or passive tracking of errors) stop new traffic from going to a failed instance. They can't save requests that are already in flight on an instance that is about to die. Connection draining handles planned removals.
  6. The load balancer itself is made redundant with an active/passive pair sharing a VIP (keepalived/VRRP), multiple DNS records, anycast, or a managed cloud LB, so it isn't a single point of failure.

Trade-offs to mention: sticky sessions skew the load; WebSockets pin one connection to one server for hours, so least-connections works better than round robin for them; a longer health-check interval means slower failure detection; and adding app servers does nothing for a database bottleneck.

Day 1

Networking and the HTTP request lifecycle

Understand how requests move through systems

Goal: Can you trace one POST /api/messages from the browser's address bar to res.json() in ChatFlow's Express app, naming every handshake, queue and process it passes through?

Checklist

DNS, TCP and TLS: getting a secure byte pipe

1. What problem does it solve?

Your browser knows a name, not an address, and IP only delivers individual packets, best-effort, possibly lost or reordered. DNS turns the name into an IP. TCP turns lossy packets into an ordered, reliable byte stream with flow and congestion control. TLS makes that stream confidential and proves the server owns the name. HTTP runs on top of all three.

2. How it works internally

  1. DNS. The OS stub resolver checks its cache (and /etc/hosts), then asks the configured recursive resolver over UDP port 53. The recursive resolver, on a cache miss, asks a root server (which refers it to the .com TLD servers), then the TLD (which refers it to the domain's authoritative servers), then the authoritative server, which returns the A/AAAA record with a TTL. Every layer (browser, OS, resolver) caches the answer for up to the TTL. Negative answers (NXDOMAIN) are cached too. If a response is too big for UDP, the server sets the truncated bit and the client retries over TCP.
  2. Socket setup. The client calls connect(). The kernel picks an ephemeral source port (Linux default range 32768-60999), so the connection is identified by the 4-tuple (src IP, src port, dst IP, dst port). Each socket is a file descriptor in the process.
  3. TCP handshake. Client sends SYN with its initial sequence number. The server kernel puts the half-open connection in the SYN queue and replies SYN-ACK. On the client's ACK, the connection moves to the accept queue (bounded by the listen() backlog; Node passes 511, capped by net.core.somaxconn). Nothing in userland has run yet: the kernel completes the handshake by itself.
  4. Reliable delivery. Every byte has a sequence number; the receiver ACKs cumulatively. If no ACK arrives within the RTO (computed from smoothed RTT and its variance, minimum around 200 ms on Linux, doubling on each retry), the sender retransmits. Three duplicate ACKs trigger fast retransmit without waiting for the timer; SACK tells the sender exactly which ranges arrived.
  5. Flow vs congestion control. Flow control protects the receiver: it advertises a receive window (rwnd) of free buffer. Congestion control protects the network: the sender keeps a congestion window (cwnd), starting at 10 segments, doubling every RTT in slow start, then growing linearly (CUBIC is the Linux default, BBR models bandwidth instead of reacting to loss). The sender may have min(rwnd, cwnd) bytes unacknowledged. This is why a fresh connection is slow and a reused one is fast.
  6. TLS 1.3 (one round trip). ClientHello carries supported ciphers, an ephemeral ECDHE key share (usually X25519), SNI (which hostname) and ALPN (h2 or http/1.1). ServerHello returns the server's key share; both sides now derive the same handshake keys, so everything after is encrypted: EncryptedExtensions, Certificate, CertificateVerify (a signature over the transcript with the certificate's private key) and Finished. The client validates the chain up to a trusted root, checks the hostname against the SAN and the validity dates, sends Finished, and can send the HTTP request in the same flight. Because keys are ephemeral, stealing the server's private key later cannot decrypt recorded traffic (forward secrecy). Resumption with a PSK enables 0-RTT data, which can be replayed, so only idempotent requests belong there.
  7. Closing. Either side sends FIN (I'm done sending); the other ACKs and later sends its own FIN. The side that closed first enters TIME_WAIT for 2 x MSL (60 s on Linux) so stray late packets can't be mistaken for a new connection on the same 4-tuple, and so the final ACK can be resent. RST is an abort: sent when data arrives for a socket that doesn't exist, when a process dies with unread data, or deliberately with SO_LINGER 0. RST skips TIME_WAIT and discards buffered data.

4. What can go wrong

Scenario: You move the API to a new IP and update DNS, but some users keep hitting the old host for hours.

What actually happens: Resolvers and browsers cached the old A record for its TTL; some resolvers clamp TTLs upward.

Fix / mitigation: Lower the TTL a day before the move, keep the old host serving (or proxying) until traffic drains, or put a stable load balancer IP in DNS so backends can change behind it.

Scenario: A load-test client opening and closing thousands of connections per second starts failing with EADDRNOTAVAIL.

What actually happens: The client is the active closer, so each closed connection sits in TIME_WAIT for 60 s holding its ephemeral port. About 28k ports per destination IP:port run out.

Fix / mitigation: Reuse connections (keep-alive, pooling), widen ip_local_port_range, enable tcp_tw_reuse for outgoing connections, or spread across more destination IPs.

Scenario: Clients see intermittent connection timeouts during a burst even though the CPU is idle.

What actually happens: The accept queue overflowed because the process was not calling accept() fast enough (e.g., the Node event loop was busy). Linux drops the final ACK, the client retransmits, and the user sees seconds of delay.

Fix / mitigation: Keep the event loop free, raise somaxconn and the backlog, add instances. Check nstat for ListenOverflows.

5. How it scales

Per connection the server pays a handshake and a TLS key exchange (CPU), plus kernel buffers and one fd. The bottleneck at scale is usually TLS CPU and connection setup latency, which is why TLS is terminated at the edge close to the user and connections are reused. More server instances spread handshakes and fds, but they do nothing for DNS TTL staleness or for the RTT between user and server; only edge locations (CDN, anycast) shorten the RTT.

6. How I used it

ChatFlow never sees TLS in production: chat-fullstack/render.yaml deploys chatflow-api as a Render web service, and Render's proxy terminates TLS and forwards plain HTTP to the Node process. That is why backend/src/app.ts sets app.set('trust proxy', env.TRUST_PROXY) in production (TRUST_PROXY: "1" in render.yaml): req.ip, which the rate limiter keys on, must come from X-Forwarded-For, not from the proxy's socket address.

TLS does appear on the database leg: backend/src/database/prisma.ts turns TLS off for local hosts (localhost, postgres) and enables it with rejectUnauthorized: true in production, so a man-in-the-middle certificate is rejected.

The load tests in backend/load/results/SUMMARY.md ran k6 on the same laptop: the socket-connect run made 19,231 connections, which is exactly where ephemeral ports and TIME_WAIT on the client side matter.

HTTP/1.1, HTTP/2, HTTP/3 and the trace into Express

1. What problem does it solve?

HTTP gives you request/response semantics (method, path, headers, status, body) over the byte stream. The versions differ in how many requests share one connection and what happens when a packet is lost.

2. How it works internally

  1. HTTP/1.1. Text framing. One request at a time per connection; the next request waits for the previous response (pipelining exists but is effectively unused). Keep-alive is the default, so the TCP+TLS connection is reused until an idle timeout. Browsers open about 6 connections per origin to get parallelism.
  2. HTTP/2. One TCP connection, binary frames tagged with a stream ID, so many requests are interleaved (multiplexed). HPACK compresses headers with a static table, a per-connection dynamic table of previously sent headers, and Huffman coding, so repeated cookies and auth headers cost a few bytes. Head-of-line blocking at the HTTP layer is gone, but TCP still delivers bytes in order: one lost segment stalls every stream on the connection until it is retransmitted.
  3. HTTP/3. Runs on QUIC over UDP. QUIC implements reliability and congestion control per stream in user space, so a lost packet stalls only its own stream. Transport and TLS 1.3 handshakes are combined (1 RTT, 0-RTT on resumption), headers use QPACK, and connections are identified by connection IDs, so a phone switching from Wi-Fi to cellular keeps the connection.
  4. Accepting in Node. The listening socket is registered with epoll. In the poll phase libuv calls epoll_wait; when the listen fd is readable, it calls accept() to pull connections off the kernel accept queue, gets a new fd per connection and registers it with epoll too. One thread waits on thousands of fds; the kernel says which ones have data.
  5. Parsing and dispatch. When bytes arrive, Node's llhttp parser builds req, the http.Server emits 'request', and Express runs the middleware stack in registration order until one sends a response.
  6. CORS preflight. If the page origin differs from the API origin and the request is not "simple" (here: Content-Type: application/json and an Authorization header), the browser first sends OPTIONS with Origin, Access-Control-Request-Method and Access-Control-Request-Headers. Only if the response allows them does it send the real request. CORS is enforced by the browser; curl ignores it.

4. What can go wrong

Scenario: Random 502s behind a load balancer, only on requests that arrive after a pause.

What actually happens: Node's server.keepAliveTimeout defaults to 5 s. The proxy's idle timeout is longer, so it reuses a connection Node has just closed (FIN in flight) and gets a reset.

Fix / mitigation: Make the backend's keep-alive timeout longer than the proxy's idle timeout (and headersTimeout longer still), or have the proxy retry idempotent requests.

Scenario: A client sends an 11 KB JSON body or malformed JSON to ChatFlow.

What actually happens: express.json({ limit: '10kb' }) throws an error with status 413 (or 400 for bad JSON). backend/src/middleware/errorHandler.ts only maps AppError, ZodError and Prisma errors, so it answers 500.

Fix / mitigation: In the error handler, honour err.status when it is a 4xx from body-parser. A 500 here is a client error mislabelled as a server error and pollutes alerts.

Scenario: The frontend works locally but in production every call fails with a CORS error in the console.

What actually happens: The preflight response lacked the page's exact origin because CORS_ORIGINS (comma-separated, scheme included) didn't list the deployed frontend URL.

Fix / mitigation: Set the exact origin; check the OPTIONS request in the Network tab, not the failing POST.

5. How it scales

Per request, the costs are parsing, middleware and your handler on one event loop. Connection reuse removes handshake costs; HTTP/2 between browser and edge reduces connection count. The bottleneck for ChatFlow's REST path is the event loop plus the database pool (~960 writes/s, ~1,270 reads/s on one process per SUMMARY.md). More instances multiply the event loops, but they share the same Postgres, so the database becomes the next limit.

6. How I used it

ChatFlow's middleware order in chat-fullstack/backend/src/app.ts: helmet(), cors({ origin: env.CORS_ORIGINS, credentials: true }), express.json/urlencoded with a 10 KB limit, globalLimiter (100 requests / 15 min / IP), /health, the four routers, a 404 handler, then errorHandler. cors() answers preflights itself with 204, so preflights never reach the rate limiter. server.ts wraps the app in createServer(app) so Socket.IO can attach to the same HTTP server and port.

The frontend client (frontend/src/lib/api.ts) sends Content-Type: application/json and Authorization: Bearer, so any cross-origin deployment triggers a preflight. It does not use cookies (fetch has no credentials: 'include'), so credentials: true on the server is not needed.

Status codes in use: 201 on create, 401 for bad credentials/token (with an expired flag from ExpiredTokenError), 403 for membership checks, 404, 409 for Prisma P2002 duplicates, 422 for Zod validation, 429 from the limiters, 503 from /health when SELECT 1 fails.

Interview questions

What happens when you type a URL and press Enter?
The browser parses the URL, checks its caches, then resolves the host: browser cache, OS cache, then the recursive resolver, which walks root, TLD and authoritative servers and caches the answer for its TTL. It opens a TCP connection with SYN, SYN-ACK, ACK; the server kernel completes that and parks the connection in the accept queue. TLS 1.3 takes one more round trip: key shares in ClientHello and ServerHello, then the server's certificate and a signature proving it holds the key, and the browser validates the chain and hostname. ALPN picks HTTP/2 or 1.1. The request goes out; at my platform's edge TLS ends and the request is forwarded to Node, where epoll wakes the event loop, the parser builds req, Express runs middleware and the route, and the handler awaits Postgres. The response streams back, the browser parses HTML and repeats this for sub-resources, reusing the connection.
TCP vs UDP: when would you choose UDP?
TCP gives an ordered, reliable byte stream with flow and congestion control, at the cost of a handshake and head-of-line blocking: a lost segment holds back everything after it. UDP sends independent datagrams with no setup, no retransmission and no ordering. I'd pick UDP when late data is worthless (voice, video, game state, where the next packet supersedes the lost one), for tiny request/response exchanges like DNS where a retry is cheaper than a handshake, or when I want to build my own transport, which is what QUIC does: it adds reliability per stream on top of UDP, so one lost packet doesn't stall unrelated streams.
Walk me through the TLS 1.3 handshake. What does the certificate actually prove?
The client sends ClientHello with its supported ciphers, an ephemeral Diffie-Hellman key share, SNI and ALPN. The server replies with its own key share, and from the two shares both sides compute the same secret, so the rest is encrypted. The server sends its certificate chain and CertificateVerify, a signature over the whole handshake transcript made with the certificate's private key, then Finished. The client checks the chain to a trusted root, the hostname against the SAN, the dates, and verifies the signature. The certificate proves that a CA vouched that this public key belongs to this name, and CertificateVerify proves the server holds the matching private key right now. The session keys come from ephemeral DH, so they're forward secret.
HTTP/2 multiplexes streams. Why can it still suffer head-of-line blocking?
HTTP/2 removed blocking at the HTTP layer: responses are split into frames with stream IDs and interleaved on one connection. But all streams share one TCP byte stream, and TCP only hands bytes to the application in order. If one segment is lost, the kernel holds every later byte, belonging to any stream, until the retransmission arrives. On a lossy mobile link that can make HTTP/2 worse than six HTTP/1.1 connections, because one loss stalls everything and only one congestion window shrinks. HTTP/3 fixes it by moving to QUIC, where ordering is per stream.
Why does TIME_WAIT exist, and you have 30,000 sockets in it. Is that a problem?
The side that closes first waits 2 x MSL, 60 seconds on Linux, so that a delayed packet from the old connection can't be accepted by a new connection with the same 4-tuple, and so it can resend the final ACK if it was lost. On a server it's usually harmless: the sockets hold almost no memory and the server's port is fixed, so the 4-tuples differ by client. It's a problem on the side making many short outbound connections, like a proxy or load generator to one backend, because each TIME_WAIT pins an ephemeral port. The fix is connection reuse first, then tcp_tw_reuse or more source/destination addresses.
Why does the browser send OPTIONS before POST /api/messages, and who handles it in your app?
The frontend and API are on different origins and the request isn't "simple": it has a JSON content type and an Authorization header. So the browser sends a preflight OPTIONS with the origin, method and headers it wants to use. In ChatFlow the cors middleware, registered right after helmet in app.ts, checks the origin against CORS_ORIGINS, replies 204 with the allow headers and ends the request, so it never reaches the rate limiter or routes. Only then does the browser send the POST. CORS doesn't protect the server from non-browser clients; that's what the JWT and rate limits are for.
Which HTTP methods are idempotent, and what happens if a client retries POST /api/messages?
GET, HEAD, OPTIONS, PUT and DELETE are idempotent: repeating them leaves the same server state. GET, HEAD and OPTIONS are also safe, meaning no side effects. POST and PATCH are not idempotent. If the client's POST times out after the server inserted the message and the client retries, ChatFlow inserts a second row and the group sees the message twice, because nothing deduplicates it. The standard fix is an idempotency key: the client generates an ID per message, the server stores it with a unique constraint and returns the existing row on a duplicate. Proxies and clients should only auto-retry idempotent methods.
502 vs 503 vs 504?
All three usually come from a proxy. 502 Bad Gateway: the proxy got an invalid response or a reset from the upstream, for example the backend closed a keep-alive connection the proxy reused, or the process crashed mid-request. 503 Service Unavailable: no healthy upstream or the service is deliberately refusing, such as ChatFlow's /health returning 503 when the database is down. 504 Gateway Timeout: the upstream accepted the request but didn't answer within the proxy's timeout, typically a slow query or a blocked event loop.

Checklist

Load balancers and reverse proxies

1. What problem does it solve?

One server is a single point of failure and has one CPU budget. A load balancer gives clients one stable address, spreads requests over many backends, stops sending to dead ones, and lets you deploy by rotating instances out. A reverse proxy is the same position in the path with more L7 jobs: TLS termination, compression, caching, routing by path.

2. How it works internally

  1. L4 (transport). Sees IPs and ports only. It picks a backend per TCP connection and forwards packets (NAT, or direct server return), or splices two TCP connections. Fast and protocol-agnostic, but it can't route by path, read headers, or balance per request: one long HTTP/2 or WebSocket connection stays on one backend.
  2. L7 (application). Terminates the client's TCP and TLS, parses HTTP, then opens (or reuses pooled) connections to backends. It can route /api and /socket.io differently, add X-Forwarded-For/X-Forwarded-Proto, retry idempotent requests, and balance each request separately. Cost: it holds two connections per client and does the TLS CPU.
  3. Choosing a backend. Round robin: next in the list. Weighted: proportional to capacity. Least connections: fewest open connections, best when request durations vary or connections are long-lived (WebSockets). IP hash: hash of client IP, a crude stickiness that breaks behind NAT or when IPs change. Consistent hashing: backends and keys placed on a ring (with virtual nodes); a key goes to the next node clockwise, so adding or removing one of N nodes moves only about 1/N of the keys. Use it when the backend holds per-key state (caches, shards).
  4. Health checks. Active: the LB probes /health every interval and ejects a backend after N failures, re-adds it after M successes. Passive: the LB watches real traffic (resets, timeouts, 5xx) and ejects outliers. Shallow checks (process alive) avoid cascades; deep checks (database reachable) can eject every instance at once when a shared dependency fails.
  5. Draining. On deploy or scale-in, the LB marks the instance draining: no new requests or connections, in-flight ones finish up to a deregistration timeout, then the instance gets SIGTERM. For WebSockets "finish" never happens on its own, so the server must close sockets and clients reconnect elsewhere.
  6. Redundancy of the LB itself. VIP + keepalived: two LB boxes speak VRRP; the active one owns a virtual IP, and on failure the backup claims it with a gratuitous ARP. DNS with multiple A records: simple, but failover waits on TTLs and client caching. Anycast: many sites announce the same IP via BGP and the network routes users to the nearest one (CDNs, Cloudflare, Vercel's edge). Managed cloud LBs (AWS ALB/NLB) are themselves fleets behind DNS that the provider scales.

The LB itself is scaled horizontally (anycast, DNS) and made redundant (VIP failover); it rarely is the bottleneck unless it terminates TLS for a huge number of new connections per second.

API gateways and WebSockets behind a balancer

1. What problem does it solve?

An API gateway centralises cross-cutting API policy (authentication, API keys, quotas, rate limits, routing to many services, request/response transformation) so each service doesn't reimplement it. A load balancer only decides which healthy instance gets the traffic. WebSockets add a twist: one HTTP request becomes a connection that lives for hours.

2. How it works internally

  1. A WebSocket starts as an HTTP/1.1 GET with Upgrade: websocket, Connection: Upgrade and Sec-WebSocket-Key. The server replies 101 Switching Protocols; from then on the TCP connection carries WebSocket frames, not HTTP.
  2. A proxy must forward the hop-by-hop Upgrade headers explicitly (that's what ChatFlow's nginx /socket.io/ block does), then pipe bytes both ways. Load balancing happens once, at connect time.
  3. Idle timeouts on every hop (LB, proxy, NAT) kill silent connections, so the protocol needs heartbeats: Socket.IO pings every pingInterval and drops the client if no pong within pingTimeout.
  4. Socket.IO's Engine.IO layer can start with HTTP long-polling: GET /socket.io/?EIO=4&transport=polling returns a sid; later polls and the upgrade request carry that sid and must reach the same process. That's why multi-instance Socket.IO needs sticky sessions unless clients are WebSocket-only.
  5. WebSocket handshakes are plain GETs, so CORS preflight never runs; the server must check Origin itself (Loom's Go service has an allowlist; Socket.IO's cors option governs the polling transport).

Interview questions

L4 vs L7 load balancing?
An L4 balancer works on TCP or UDP: it sees addresses and ports, picks a backend per connection and forwards packets or splices connections. It's fast and protocol-agnostic but can't route by URL or balance individual requests on a reused connection. An L7 balancer terminates the client's connection and TLS, parses HTTP, and makes a decision per request: route /api to one pool and /socket.io to another, add forwarding headers, retry idempotent requests, do cookie stickiness. It costs more CPU and memory and adds timeouts you must tune. Typical setup: L4 or anycast at the very edge for raw scale, L7 behind it for routing.
How do health checks work, and what's wrong with a health check that queries the database?
Active checks: the balancer calls an endpoint on an interval and removes the instance after a few consecutive failures, adding it back after a few successes. Passive checks watch live traffic for errors and timeouts. ChatFlow's /health runs SELECT 1 and returns 503 on failure. That's good for catching a misconfigured instance at deploy time, but in steady state a shared database outage fails every instance at once, the balancer ejects all of them, and you've turned a partial outage into a total one. I'd split it: a liveness check that only proves the process responds, and a dependency status that's alerted on but doesn't drive routing.
How would you run ChatFlow on three instances?
An L7 balancer with least-connections for /socket.io/ and round robin for /api/. The client already prefers WebSocket, but for the polling fallback I'd add cookie-based stickiness on /socket.io/, because the Engine.IO session ID lives in one process. Then @socket.io/redis-adapter, so io.to(groupId).emit on one instance is published through Redis and each instance writes to its local sockets. The onlineUsers map and the rate limiter counters move to Redis too. Graceful shutdown must close sockets so clients reconnect elsewhere. Finally, total pool size across instances has to stay under Postgres max_connections.
Consistent hashing: why not just hash(key) mod N?
With mod N, changing N from 4 to 5 remaps about 80% of keys, which for a cache means a near-total miss storm. Consistent hashing places nodes and keys on a ring; each key belongs to the next node clockwise. Adding a node only takes keys from its neighbour, so about 1/N of keys move. Virtual nodes, many points per physical node, smooth out the uneven arc sizes. I'd use it when backends hold per-key state, like cache shards; for stateless HTTP, least connections is better.
What's connection draining and how does it interact with WebSockets?
During a deploy the balancer stops sending new connections to the instance but lets in-flight requests finish, up to a timeout, then the instance is sent SIGTERM. For short HTTP requests that's clean. A WebSocket never finishes on its own, so draining just waits out the timeout and then the connection is cut. Better: on SIGTERM the server closes its sockets itself, ideally spread over a few seconds, and clients reconnect with jittered backoff to the remaining instances. Clients must also resync anything they missed, because messages sent during the gap are lost unless there's a replay mechanism.
How is the load balancer itself not a single point of failure?
Several ways. Two LB machines with keepalived: they run VRRP, the primary owns a virtual IP, and if it dies the backup takes over the IP and announces it with a gratuitous ARP, within seconds. DNS with several LB addresses, which is simple but failover depends on TTLs and client caching. Anycast: the same IP announced over BGP from many locations, so routing sends users to the nearest healthy site and withdraws a dead one. Or a managed cloud LB, which is a provider-run fleet behind DNS. My projects use the last two implicitly: Vercel's edge and Render's proxy.

  • Per-process state breaks under scale-out - in-memory rate limits, Socket.IO rooms and the onlineUsers map all silently become per-instance. That's the real work in scaling ChatFlow, not the balancer config.
  • Upstream keep-alive - a proxy that opens a new connection to the backend per request wastes handshakes; nginx needs an upstream block with keepalive and proxy_set_header Connection "".

Node.js, OS processes and concurrency

Understand how requests move through systems

Goal: Why did one ChatFlow process hold 5,000 sockets easily but saturate at ~170k offered deliveries/s, and what exactly runs on the main thread vs the libuv threadpool vs the kernel?

Checklist

The Node.js event loop and libuv

1. What problem does it solve?

Servers spend most of their time waiting on the network and the database. A thread per connection wastes memory and context switches on waiting. Node runs your JavaScript on one thread and lets the kernel (epoll) and a small threadpool do the waiting, so one process can hold thousands of connections. The price: any CPU work in JavaScript blocks everyone.

2. How it works internally

  1. Process vs thread. A process has its own address space, fds and at least one thread; a crash is contained. Threads in a process share memory and fds; they're cheaper to create and switch, but share fate. A Node process has one JS thread (the event loop), V8 helper threads (GC, compilation) and the libuv threadpool (4 threads by default).
  2. One loop iteration. timers: run setTimeout/setInterval callbacks whose time has passed. pending callbacks: some deferred system callbacks (certain TCP errors). idle/prepare: internal. poll: call epoll_wait with a timeout up to the nearest timer, then run I/O callbacks (new connections, socket data, completed threadpool jobs); if nothing else is scheduled it blocks here. check: setImmediate callbacks. close callbacks: 'close' events. The loop exits when nothing keeps it alive.
  3. Microtasks. After every single callback (and between each timer or immediate since Node 11), Node drains the process.nextTick queue first, then the promise microtask queue, repeating until both are empty. An await continuation is a promise microtask. So a recursive nextTick or promise chain starves I/O entirely.
  4. Ordering. In the main module, setTimeout(fn, 0) vs setImmediate order is not deterministic (depends on whether 1 ms has passed when the loop starts). Inside an I/O callback, setImmediate always runs first, because check comes right after poll.
  5. Threadpool. Work with no non-blocking OS interface runs there: filesystem calls, dns.lookup (blocking getaddrinfo), async crypto.scrypt/pbkdf2/randomBytes with a callback, async zlib. When a job finishes, its callback is queued for the poll phase. Size: UV_THREADPOOL_SIZE (default 4, max 1024), set before the pool is first used, in practice via the environment. TCP sockets are not in the pool; they use epoll directly. dns.resolve* uses c-ares on the main loop, not the pool.
  6. Blocking. Synchronous CPU work (big JSON.stringify, a sync hash, a regex with catastrophic backtracking, a large loop) holds the thread: timers fire late, sockets aren't read, the accept queue fills. Measure with perf_hooks.monitorEventLoopDelay() and profile with --cpu-prof.

What actually happens: auth.service.ts uses promisify(scrypt), which runs on the 4-thread pool. scrypt is deliberately slow and memory-hard (default cost about 16 MB per hash), so only 4 hashes run at once and the rest queue. dns.lookup and fs calls wait behind them in the same queue.

Fix / mitigation: Raise UV_THREADPOOL_SIZE toward the core count, keep the auth limiter, and never switch to scryptSync, which would block the event loop itself.

Scenario: At 400 msg/s into rooms of ~433 sockets, p50 latency jumps from tens of ms to 11 s and 8,323 messages are lost (socket-fanout-2000.json).

What actually happens: Each message costs main-thread work: Zod parse, handling the Prisma result, serialising the packet, then a WebSocket frame write per recipient. Offered work exceeded one core, so callbacks queued faster than the loop drained them; latency is queueing delay.

Fix / mitigation: More processes (cluster or instances) with the Redis adapter; smaller fan-out per message; batching.

Scenario: await in a loop: for (const { groupId } of memberships) await socket.join(groupId).

What actually happens: Harmless here (in-memory adapter join is cheap), but the same pattern with network calls serialises N round trips.

Fix / mitigation: socket.join([...ids]) accepts an array; for network calls use bounded Promise.all.

5. How it scales

One process scales with connections until its single core is busy; then you need more processes. Doubling processes doubles CPU for HTTP handlers and per-socket writes, but not for anything shared: every process still sees every broadcast through the Redis adapter, all processes share one Postgres, and each brings its own connection pool. Raising the threadpool helps only threadpool-bound work (scrypt, fs).

Pools, shutdown and backpressure

1. What problem does it solve?

A Postgres connection is a backend process on the server (several MB, a TLS handshake and auth to open), so you reuse a small pool. Shutdown must stop taking work and finish in-flight work before the platform kills you. Backpressure stops a fast producer from buffering unbounded data in memory for a slow consumer.

2. How it works internally

  1. Pool. pg.Pool keeps up to max connections (default 10). A query checks one out, and if all are busy the request waits in a queue (forever by default unless connectionTimeoutMillis is set). Idle ones close after idleTimeoutMillis. Prisma 7 with @prisma/adapter-pg uses a pg pool underneath.
  2. Pool math. Instances x pool size must stay under Postgres max_connections (100 in the ChatFlow load test) minus reserved slots. Serverless multiplies instances unpredictably, so you put PgBouncer or the provider's pooler (transaction mode) in front.
  3. Graceful shutdown. The platform sends SIGTERM, waits a grace period, then SIGKILL. The handler should: fail readiness, call server.close() (stops listening; since Node 19 also closes idle keep-alive connections), close long-lived connections it owns (io.close() for Socket.IO), wait for in-flight requests, close the DB pool, then exit 0, with a hard timeout shorter than the grace period.
  4. Backpressure. writable.write(chunk) returns false once the internal buffer passes highWaterMark (64 KiB by default for byte streams on Node 22). The producer should stop and resume on 'drain'. stream.pipeline() does this and propagates errors and cleanup. Ignoring the return value means memory grows until the process dies. For sockets, a slow client's unsent data accumulates in the server's per-socket buffer.

Node is single-threaded. How does it handle 5,000 concurrent connections?

In the poll phase, libuv asks the kernel which sockets have data, runs the callback for each, and goes back to waiting. An idle WebSocket costs memory and an fd, not CPU, so holding 5,000 is cheap; ChatFlow did it with zero loss. Things the OS can't do non-blockingly, like file I/O, dns.lookup and scrypt, go to a small threadpool. The limit isn't connections, it's how much JavaScript each event costs: ChatFlow saturated when fan-out work exceeded one core, around 170k offered deliveries per second.
Explain the event loop phases and where microtasks run.
Each iteration goes: timers, which runs due setTimeout and setInterval callbacks; pending callbacks for some deferred system errors; an internal idle/prepare step; poll, where it waits in epoll up to the next timer and runs I/O callbacks; check, which runs setImmediate; and close callbacks. PostgreSQL internals

Understand how data is stored and accessed

Goal: When two requests change the same row at the same time, what does Postgres physically do, what does each request see, and which bug can still get through?

Checklist

PostgreSQL

1. What problem does it solve?

You need many clients to read and change shared data at the same time, never see half-done changes, and never lose a committed change if the machine dies. Postgres gives you that with a declarative query language, a cost-based planner that chooses how to fetch the data, MVCC so readers and writers do not block each other, and a write-ahead log so a commit survives a crash.

2. How it works internally

  1. Connection. The postmaster forks one OS backend process per client connection. That process holds your session state, and it is why connections are expensive (memory per process, and every snapshot has to scan all active backends).
  2. Parse and analyze. The parser checks syntax and builds a raw tree. The analyzer resolves table and column names against the system catalogs and produces a query tree.
  3. Rewrite. Rules are applied; most importantly, views are expanded into their underlying query.
  4. Plan. The planner enumerates access paths (seq scan, index scan, bitmap scan) and join orders and algorithms (nested loop, hash, merge), estimates rows from pg_statistic (filled by ANALYZE: most-common values, histograms, n_distinct) and picks the cheapest total cost. Costs are in abstract units: seq_page_cost=1, random_page_cost=4 by default.
  5. Execute. The plan is a tree of nodes. The top node asks its child for the next row, which asks its child, and so on (the "pull" or Volcano model). That is why LIMIT 20 over an ordered index scan stops after 20 rows.
  6. Page access. Every table (the heap) and index is a file of 8 KB pages. Nodes read pages through shared_buffers; a miss goes to the OS page cache, then disk.
  7. Writes (MVCC). An UPDATE never overwrites in place. It writes a new tuple version with xmin = your transaction id and stamps the old version's xmax with the same id. A DELETE only sets xmax.
  8. Visibility. A snapshot records which transactions were finished when it was taken. A tuple is visible if its xmin committed before your snapshot and its xmax is empty, aborted, or not yet visible to you. Commit status lives in pg_xact. Read Committed takes a new snapshot per statement; Repeatable Read keeps one for the whole transaction.
  9. WAL and commit. Every change is first described in a WAL record. At COMMIT, the WAL up to that record is flushed (fsync) to disk; the changed data pages stay dirty in memory. The rule: a data page may never reach disk before the WAL that describes it.
  10. Checkpoint and recovery. A checkpoint writes all dirty pages and records a redo point. After a crash, Postgres replays WAL from the last redo point forward, so committed work comes back and uncommitted work stays invisible (its xids never committed). The first change to a page after a checkpoint logs the full page, which protects against torn 8 KB writes.
  11. VACUUM. Dead versions stay in the heap until (auto)vacuum removes those no running snapshot can still see, records the free space in the free-space map, updates the visibility map (which makes index-only scans possible), and freezes old xids to avoid 32-bit wraparound. It does not shrink the file; VACUUM FULL rewrites the table under an exclusive lock.

4. What can go wrong

Scenario: You add an index on status and the query WHERE status = 'active' gets slower or ignores the index.

What actually happens: 90% of rows are active. An index scan would do one random heap read per row; reading the whole table sequentially is cheaper, so the planner (correctly) picks a seq scan. Meanwhile every INSERT and every update of status now also writes the index, its WAL, and blocks HOT updates (an update that changes an indexed column cannot stay on the same page as a heap-only tuple).

Fix / mitigation: Index selective predicates only; use a partial index (WHERE status = 'pending') for the rare value; drop unused indexes (pg_stat_user_indexes.idx_scan = 0).

Scenario: A transaction left open for hours (an idle-in-transaction connection, a long report).

What actually happens: Its snapshot is the oldest, so VACUUM cannot remove any version that became dead after it started, on any table. Tables and indexes bloat, scans read mostly dead tuples, and index-only scans start fetching the heap.

Fix / mitigation: idle_in_transaction_session_timeout, statement_timeout, keep transactions short, monitor pg_stat_activity.xact_start.

Scenario: Two admins of a ChatFlow group remove each other at the same moment.

What actually happens: removeMember counts admins (2), then deletes. Both requests read 2 under Read Committed, both pass the "not the last admin" check, both delete. The group has zero admins. This is write skew: each transaction changed a different row, so no row lock ever conflicts. Repeatable Read does not catch it either.

Fix / mitigation: In one transaction, lock the parent row first (SELECT 1 FROM "Group" WHERE id = $1 FOR UPDATE) so membership changes in one group serialize, then count and delete. Or run at SERIALIZABLE and retry on 40001.

Scenario: Transaction A locks row 1 then row 2; transaction B locks row 2 then row 1.

What actually happens: Each waits for the other. After deadlock_timeout (1 s) a backend checks the wait-for graph, finds the cycle, and aborts one with 40P01 deadlock detected.

Fix / mitigation: Always lock in a fixed order (sort ids), keep transactions short, retry the victim.

5. How it scales

The first bottleneck is usually connections, not queries: each is a process, and max_connections defaults to 100. Every app instance has its own pool, so 20 instances with pool size 10 already need 200. Put PgBouncer (or Supabase's pooler) in front in transaction mode: a server connection is lent to a client only for one transaction. That breaks anything tied to a session: SET, session advisory locks, LISTEN, and (unless the pooler supports it) named prepared statements.

Reads scale with streaming replicas: the primary ships WAL, replicas replay it. Replication is usually asynchronous, so a replica can lag and a user may not see their own write; send reads that follow a write to the primary. Writes do not scale with replicas at all: there is one primary. Past that you partition tables, or shard by key (Citus, or app-level routing), and lose cross-shard joins and transactions. More app instances fix CPU in your Node process; they make the database problem worse.

Interview questions

What happens inside Postgres when you run a SELECT?
My connection is served by its own backend process forked by the postmaster. The parser checks syntax, the analyzer resolves table and column names against the catalogs, the rewriter expands views, and the planner builds candidate plans: seq scan or index scans for each table, and nested-loop, hash or merge joins. It estimates row counts from statistics gathered by ANALYZE and picks the plan with the lowest cost. The executor then runs the plan tree in a pull model: the top node asks its child for a row, recursively, so a LIMIT can stop early. Pages come from shared_buffers, or from the OS cache or disk on a miss, and every tuple is checked against my snapshot for visibility.
A query is slow. How do you use EXPLAIN ANALYZE?
I run EXPLAIN (ANALYZE, BUFFERS), which executes the query and shows each node with estimated and actual rows, time and loops. First I look for the node where estimated rows are far from actual rows, because a bad estimate leads to a bad plan, for example a nested loop chosen for what turned out to be 100,000 rows. The usual causes are stale statistics, which ANALYZE fixes, or correlated columns, which extended statistics fix. Next I look at Rows Removed by Filter on a seq scan, which means a missing or unusable index. Then at buffers read versus hit, to see whether time is going to disk. I remember to multiply per-loop numbers by loops, and I wrap writes in a transaction I roll back.
When does an index make a query slower, or get ignored?
Reads first. An index scan costs a tree walk plus one random heap fetch per matching row. If the predicate matches a large share of the table, say 30% or more, reading the whole table sequentially is cheaper, so the planner ignores the index, and if it is forced to use it the query gets slower. Then writes. Every insert must update every index, every index change produces WAL, and an update that touches an indexed column cannot be a HOT update, so it also writes new entries into every index. Indexes also take cache space away from the heap. So I add an index only for a selective, frequent query, I use partial indexes for rare values, and I drop indexes whose idx_scan stays at zero.
Explain MVCC. What does an UPDATE physically do?
Postgres keeps several versions of a row. Each tuple header has xmin, the transaction that created it, and xmax, the one that deleted or locked it. An UPDATE writes a whole new tuple with xmin set to my transaction id and sets xmax on the old one. A reader's snapshot lists which transactions had finished when it was taken. A version is visible if its creator committed before the snapshot and its deleter did not. That is why readers never block writers. The cost is dead tuples: once no snapshot can see an old version, VACUUM marks its space reusable and updates the visibility map. A long-running transaction holds that horizon back, which causes bloat.
What is the WAL and how does crash recovery work?
The write-ahead log is an append-only record of every change. The rule is that the WAL record describing a change must reach disk before the changed data page does. On commit, Postgres flushes WAL up to the commit record; the data pages stay dirty in shared_buffers and are written later by the background writer and the checkpointer. A checkpoint flushes all dirty pages and records a redo point. After a crash, Postgres replays WAL from the last redo point, so every committed change is reapplied. Transactions with no commit record stay invisible, because visibility depends on commit status. Full-page images after each checkpoint protect against half-written pages. Replicas work by streaming the same WAL.
What are Postgres's isolation levels and what does each allow?
There are three effective levels; Read Uncommitted behaves like Read Committed. Read Committed is the default: each statement gets a fresh snapshot, so two reads in one transaction can disagree. If my UPDATE hits a row someone else is changing, I wait, then re-check my WHERE against the new version. Repeatable Read takes one snapshot for the whole transaction. In Postgres that also prevents phantoms. If I try to update a row that changed after my snapshot, I get a serialization error and must retry. It still allows write skew. Serializable adds SSI: it tracks read-write dependencies between concurrent transactions and aborts one with 40001 when they could not have happened in any serial order.
What is a lost update and how do you prevent it?
Two requests read a balance of 100, each adds 10 in application code, and both write 110. One increment is lost. Fixes, from simplest: first, make it one atomic statement, UPDATE ... SET balance = balance + 10, because the row lock and the re-check under Read Committed serialize the two updates. Second, a pessimistic lock: SELECT ... FOR UPDATE inside the transaction, so the second reader waits. Third, optimistic concurrency: keep a version column and run UPDATE ... SET ..., version = version + 1 WHERE id = $1 AND version = $2; zero rows updated means someone else won, so reload and retry. Fourth, Repeatable Read or Serializable, which raises an error you retry. Loom's billing upsert is the optimistic pattern, with the Stripe event timestamp as the version.
Follow-up: Is ChatFlow's "cannot remove the last admin" check safe under concurrency?
No. It counts admins and then deletes as two separate statements, not even in one transaction. If two admins remove each other at the same time, both counts return 2, both checks pass, and both deletes run. They delete different rows, so no row lock conflicts, and Repeatable Read would not catch it either; it is write skew. Two fixes. One: an interactive Prisma transaction that first locks the group row with SELECT ... FOR UPDATE, so all membership changes for that group run one at a time, then counts and deletes. Two: run the transaction at Serializable and retry on 40001. I would pick the group-row lock, because it is easy to explain and the contention is tiny.
Follow-up: Two Stripe webhooks for the same event arrive at once in Loom. Walk me through it.
Both open a transaction and run INSERT INTO stripe_webhook_event ... ON CONFLICT (event_id) DO NOTHING. The first inserts. The second hits the unique index entry that the first, still uncommitted, transaction has inserted, so it waits for that transaction. If the first commits, the second's insert becomes a no-op with rowCount 0, and the code rolls back and returns false. If the first rolls back, the second's insert succeeds and it processes the event. Because the claim is in the same transaction as the billing update, a crash never leaves an event marked processed without its effect. Separately, the upsert's WHERE on last_stripe_event_created stops an older event from overwriting a newer one.
Follow-up: Why not just raise max_connections to 2000? What does PgBouncer transaction mode break?
Each connection is an OS process with its own memory, and work like taking a snapshot scans all backends, so throughput usually drops past a few hundred active connections because of context switching and contention. Most app connections are idle anyway. A pooler lets thousands of clients share a few dozen server connections. In transaction mode a server connection is assigned only for one transaction, so anything that relies on session state breaks: SET without LOCAL, session-level advisory locks, LISTEN/NOTIFY, temporary tables, and named prepared statements unless the pooler tracks them. Loom's migration advisory lock, for example, must run on a direct or session-mode connection.
Follow-up: How would you add a NOT NULL column to a 100-million-row table without downtime?
Expand, migrate, contract. First, add the column as nullable, or with a constant default; since Postgres 11 that is a metadata-only change and does not rewrite the table. Set a short lock_timeout so the ALTER fails fast instead of queueing behind a long query and blocking everyone behind it. Second, deploy code that writes the new column. Third, backfill in small batches by primary key range, so no transaction is long and WAL and replicas keep up. Fourth, add CHECK (col IS NOT NULL) NOT VALID, then VALIDATE CONSTRAINT, which scans without blocking writes. Since Postgres 12, SET NOT NULL can use that validated check and skip the scan. Indexes go in with CREATE INDEX CONCURRENTLY.

1. What problem does it solve?

You need shared state that many app instances can read and change in well under a millisecond: counters, sessions, rate limits, queues, live event logs, and a cache in front of a slower database. Redis keeps everything in memory, offers typed data structures with atomic operations on them, and runs scripts atomically, so you get correct read-modify-write without distributed locks.

2. How it works internally

  1. One command thread. An event loop (epoll) accepts connections and parses requests, and a single thread executes commands one at a time. Since 6.0, optional I/O threads can read and write sockets, but execution stays single-threaded. Every command is therefore atomic, and there are no locks. The cost is that any O(N) command (KEYS *, HGETALL on a huge hash, DEL of a big key, a slow Lua script) stalls every client. Use SCAN and UNLINK instead.
  2. Keyspace. A hash table maps key to value object. Each type switches encoding with size: hashes, sets and sorted sets start as a compact listpack and become a hashtable (sorted sets: a skiplist plus a hashtable, giving O(log N) rank and range plus O(1) score lookup). Lists are a quicklist of listpacks. Streams are a radix tree of listpacks keyed by entry id.
  3. Expiry. Keys with a TTL also sit in an expires dict. Lazy: any access checks the TTL and deletes an expired key first. Active: about 10 times a second Redis samples 20 keys from expires, deletes the expired ones, and repeats while a large share of the sample was expired (classically more than 25%; newer versions tune this with active-expire-effort). So memory from expired keys is reclaimed even if nobody reads them, just not instantly. Replicas do not expire keys themselves; the primary sends a DEL.
  4. Eviction. When maxmemory is reached, the policy decides: noeviction (writes fail with an OOM error), allkeys-lru/lfu, volatile-lru/lfu/ttl (only keys with a TTL), or random variants. LRU is approximate: Redis samples a few keys (maxmemory-samples, default 5) and evicts the best candidate from a pool.
  5. Persistence. RDB: fork(), and the child writes a point-in-time snapshot while the parent keeps serving; copy-on-write duplicates only pages the parent changes. You lose everything since the last snapshot. AOF: every write command is appended; appendfsync everysec (default) loses at most about a second, always fsyncs each write (slow), and a background rewrite compacts the file. Most deployments use AOF with an RDB preamble.
  6. Replication. A replica sends PSYNC with replication id and offset. If the primary's backlog still has that offset, it streams only the missing commands; otherwise it sends a full RDB and then streams. Replication is asynchronous, so a write acknowledged by the primary can be lost if it dies before the replica receives it. WAIT narrows that window but does not close it.
  7. Sentinel and Cluster. Sentinels watch the primary; when a quorum agrees it is down, one is elected leader and promotes a replica, and clients ask the Sentinels for the current primary. Cluster splits the keyspace into 16384 slots, CRC16(key) mod 16384, spread across primaries. A client sent to the wrong node gets MOVED. Multi-key commands and scripts must touch keys in one slot, or they fail with CROSSSLOT. A hash tag {...} hashes only the braced part, which forces related keys into one slot.
  8. Scripts and transactions. EVAL runs a Lua script on the command thread with nothing interleaved: you can read, branch and write atomically. MULTI/EXEC queues commands and runs them back to back, but you cannot read a value and branch on it inside. WATCH adds optimistic check-and-set: EXEC returns nil if a watched key changed. Neither rolls back: if a command fails at runtime, the writes before it stay.
  9. Streams. XADD key [MAXLEN ~ n] id field value appends an entry; ids are ms-seq and must strictly increase. XRANGE and XREAD [BLOCK] read by id. Consumer groups keep a last-delivered id per group; XREADGROUP ... > hands new entries to one consumer and records them in that consumer's Pending Entries List (PEL) until XACK. XPENDING and XAUTOCLAIM move stuck entries from a dead consumer to a live one, so delivery is at-least-once. Pub/Sub, by contrast, stores nothing: a message goes to whoever is subscribed right now and is gone.

4. What can go wrong

Scenario: Cache-aside with "update DB, then delete the cache key", under concurrency.

What actually happens: Reader A misses and reads the old row from the DB. Writer B updates the row and deletes the key. A then writes the old value it read into the cache. The cache now holds stale data until the TTL expires, and nothing will correct it earlier.

Fix / mitigation: Always set a TTL (it bounds the staleness), delete rather than update on write, store a version and refuse to overwrite a newer one (a small Lua script), or invalidate from the database change stream.

Scenario: A hot key expires and 5,000 requests miss at the same moment (cache stampede).

What actually happens: All 5,000 run the same expensive query; the DB connection pool saturates and latency spikes for everything.

Fix / mitigation: Only one rebuilder: SET lock:k token NX PX 5000, others serve stale data or wait briefly. Coalesce in process (one in-flight promise per key). Refresh early, before expiry (probabilistic early expiration, or a background refresher). Add random jitter to TTLs so keys written together do not expire together.

Scenario: Loom's Redis primary fails over to a replica that had not yet received the last few writes.

What actually happens: Those events vanish from the stream and eventCount moves back. The EventBus keeps its in-memory sequence, so the next event gets a higher number and is accepted; the stream now has a hole. A browser asking for "after N" receives a gap it cannot fill.

Fix / mitigation: Make the script require sequence == current + 1 and fail the run on a gap. Use WAIT 1 on critical writes. Archive finished runs to Postgres. Do not call Redis "durable" without naming the window.

Scenario: Redis reaches maxmemory with an allkeys-lru policy while it holds Loom's run hashes.

What actually happens: Redis may evict loom:run:{id}, which is the ownership record, so the replay route returns 404 for a live run. Eviction is correct for a cache and wrong for a source of truth.

Fix / mitigation: noeviction for source-of-truth data (writes fail loudly, and Loom already turns Redis errors into 503), with memory alerts; put a real cache in a separate instance.

5. How it scales

One instance is bounded by one core for execution and by RAM. Read replicas add read throughput but are asynchronous, so reads can be stale. Cluster adds write throughput and memory by splitting slots across primaries; what it does not fix is a single hot key, since a key lives in exactly one slot on one node. Shard the key itself (counter:{n}) or cache it in process. Cluster also constrains your code: every multi-key script or MULTI needs a hash tag. Loom's PERSIST_EVENT touches loom:run:R, loom:run:R:events and loom:owner:U:runs, which hash to different slots, so it would fail with CROSSSLOT. Rename to loom:run:{R} and loom:run:{R}:events, and move the owner-index ZADD into a separate idempotent call. More app instances do not help Redis; they add connections and load to it.

Interview questions

Redis is single-threaded. Why is it fast, and what is the catch?
Commands run one at a time on a single thread, which removes locks and context switching. The data is in memory, and most operations are O(1) or O(log N) on compact structures, so one core can handle on the order of a hundred thousand simple operations per second. Network I/O can be spread over I/O threads in newer versions. The catch is that one slow command blocks everyone: KEYS *, deleting a huge key, HGETALL on a giant hash, or a long Lua script. So I use SCAN and UNLINK and keep scripts to a handful of commands. The same single thread is also what makes every command, and every script, atomic.
How do TTLs and expiry actually work?
A key with a TTL is also recorded in an expires dictionary with its deadline. There are two mechanisms. Lazy: whenever a command touches a key, Redis checks its deadline and deletes it first if it has passed, so a client never reads an expired value. Active: about ten times a second Redis samples 20 keys that have TTLs, deletes the expired ones, and repeats the round while a large share of the sample was expired. So an expired key that nobody reads still gets reclaimed, just not instantly. On replicas, the primary sends explicit DELs to keep the data consistent. If many keys share the same TTL, they expire together, which is why I add jitter.
Which eviction policy would you choose?
It depends on whether Redis is a cache or a store. For a pure cache I use allkeys-lfu, or allkeys-lru: any key can go, and keeping the frequently used ones maximizes the hit rate. volatile-lru suits a mixed instance where only keys with a TTL may be evicted. For data that is the source of truth, like Loom's run records and rate-limit counters, I use noeviction. Writes then fail with an OOM error instead of silently dropping an ownership record, and Loom already turns Redis errors into a 503. LRU in Redis is approximate: it samples a few keys and evicts the best candidate, which is close enough and needs no global list.
RDB vs AOF: what do you lose on a crash?
RDB is a periodic snapshot. Redis forks, and the child writes the dataset while the parent keeps serving; copy-on-write means memory is duplicated only for pages that change during the snapshot. A crash loses everything since the last snapshot, which could be minutes. AOF logs every write command. With appendfsync everysec, the default, you lose about one second; with always, nearly nothing, at a large throughput cost. The AOF is rewritten in the background to stay compact, and modern Redis starts it with an RDB snapshot for fast loading. Separately, replication is asynchronous, so a failover can lose acknowledged writes even when persistence is perfect.
Walk me through cache-aside and invalidation.
Read path: look in the cache; on a hit, return it. On a miss, read the database, write the value to the cache with a TTL, and return it. Write path: update the database first, then delete the cache key. I delete instead of setting the new value, because two concurrent writers could otherwise leave the older value in the cache. There is still a race. A reader misses and reads the old row, a writer updates the row and deletes the key, and then the reader writes its old value back into the cache. The TTL bounds how long that lasts. If that is not enough, I store a version with the value and only overwrite older versions, or drive invalidation from the database's change stream.
How do you prevent a cache stampede?
A stampede is many requests missing the same hot key at once and all hitting the database. First, let only one request rebuild: it takes a short lock with SET lock:key token NX PX 5000; the others wait briefly and re-read, or serve the stale value. Within one process, coalesce: keep one in-flight promise per key so concurrent callers await the same database call. Second, refresh early: rebuild before expiry, either in the background or with probabilistic early expiration, where each read near expiry has a growing chance to refresh. Third, add random jitter to TTLs so keys written together, for example after a deploy, do not all expire in the same second.
Pub/Sub vs Streams vs Kafka?
Pub/Sub is fire-and-forget. PUBLISH pushes to whoever is subscribed right now and stores nothing, so a disconnected subscriber misses messages, and a slow one is disconnected when its output buffer fills. Streams are a stored, append-only log with ids. You can read any range, block for new entries, and use consumer groups: each entry goes to one consumer, sits in that consumer's pending list until XACK, and can be claimed by another consumer if the first dies. That is at-least-once delivery. But a stream lives in memory, so you trim it. Kafka is a replicated log on disk, partitioned for scale, with retention measured in days, many independent consumer groups, and ordering per partition. Loom uses a Stream for per-run replay and Kafka for the cross-service mirror.
Explain your Lua script. Why Lua and not MULTI/EXEC?
It persists one run event in three keys: the run hash, the event stream and the owner's run index. It reads eventCount; if that is already at or past this event's sequence, it returns 0 and writes nothing. Otherwise it adds the run to the owner index on run.start, writes the hash fields, appends to the stream with the explicit id sequence-0 and approximate MAXLEN trimming, refreshes TTLs, and returns 1. The caller publishes to Kafka only on a 1. I needed Lua because the decision depends on a value read inside the operation. MULTI/EXEC only queues commands; it cannot branch on a read. WATCH could do it optimistically but retries under contention. A script runs alone on the command thread, so no other client can see the hash updated without the stream.
Follow-up: So the deterministic stream id is what makes a replay a no-op?
Not quite, and I'd correct my own wording there. The eventCount check is what makes it a no-op. If I relied only on the id, XADD with an id at or below the stream's last id would not silently skip; it would return an error. And because Redis scripts do not roll back, the HSET that ran before it would stay applied. The explicit id is a second safeguard that fails loudly. Its real value is that stream ids equal sequence numbers, so "give me everything after 41" is a single XRANGE with an exclusive start at 41-0. The check also accepts any higher sequence, not exactly current + 1, so a lost write leaves a hole. I'd tighten that.
Follow-up: Does a Lua script or MULTI/EXEC roll back on error?
No. Both are atomic in the sense of isolation: nothing interleaves. Neither is atomic in the sense of all-or-nothing. In MULTI, a syntax error at queue time makes EXEC abort the whole transaction, but a runtime error, like INCR on a hash, fails only that command and the rest still run. In a script, a redis.call error stops the script, and every write before it stays. So you validate and read first, then write, and order writes so a failure part-way leaves a safe state. Also, a script that runs past the busy threshold, 5 seconds by default, gets BUSY replies to other clients; once it has written, it cannot be killed without shutting down without saving.
Follow-up: Does ChatFlow use Redis? How would you run it on three instances?
No, it does not. Presence is an in-process Map and Socket.IO rooms are in memory, so with three instances behind a load balancer, a message sent on instance A would not reach sockets connected to B or C. I would add the Socket.IO Redis adapter, which publishes each room broadcast over Redis Pub/Sub so every instance emits to its local sockets. Losing a message during a Redis blip is tolerable there, because the message is already in Postgres and clients refetch history. Presence would move to Redis, as a set per user with expiring keys refreshed by heartbeat, so a crashed instance does not leave users stuck online. Load-test results showed the single-process ceiling is the broadcast loop, which this spreads across instances.

Added: what the original plan left out

  • Lua vs MULTI/EXEC vs WATCH - the precise atomicity question interviewers use to separate "used Redis" from "understands Redis". Lua: read, branch and write with nothing interleaved. MULTI: a fixed batch of writes run back to back. WATCH: optimistic check-and-set, with EXEC returning nil if a watched key changed. None of them roll back.
  • Hash tags and CROSSSLOT - the first thing that breaks when you move to Cluster. Keys a script touches must share a slot; {runId} in the key name forces that. Pass every key through KEYS[], never build key names inside the script, or Cluster cannot route it.
  • Hot keys and big keys - a single key lives on one node and is processed by one thread, so sharding does not help it. Split a hot counter into N sub-keys and sum them; split a big hash; delete big keys with UNLINK (freed in a background thread).
  • Client-side failure policy - ioredis queues commands while disconnected by default, so requests hang and then all fire at once. Loom disables the offline queue and caps retries so a Redis outage becomes a fast 503, and it uses jittered backoff so many clients do not reconnect in lockstep.
  • Fixed vs sliding window rate limits - Loom's INCR + EXPIRE window allows up to twice the limit across a window boundary. A sliding log (a sorted set of timestamps), a sliding counter (weighted current and previous window) or a token bucket in Lua fixes that.

Understand communication and concurrency

Goal: Can you trace one record from producer.send() to a committed consumer offset, say exactly where it can be lost or duplicated, and explain why Loom chose to lose it rather than fail a run?

Checklist

Apache Kafka

1. What problem does it solve?

You have producers that emit events faster or at different times than consumers can use them, and more than one consumer wants the same events. A plain queue (RabbitMQ classic queue, SQS) deletes a message once one consumer acks it, so a second team needs a second queue and the producer has to know about it. Kafka instead stores events in an append-only, replicated log that is kept for a retention period whatever consumers do. Each consumer group tracks its own position (offset), so you add a new reader without touching the producer, and a reader can rewind and replay. The log is split into partitions so that writes and reads scale horizontally, and ordering is kept where you need it, per key.

2. How it works internally

Storage. A partition is a directory on a broker, for example loom.swarm.events-3/. Inside are segments: 00000000000000000000.log holds record batches back to back, and the filename is the segment's base offset. Next to each .log are a sparse .index (offset to byte position, one entry roughly every 4 KB) and a .timeindex (timestamp to offset). Only the newest (active) segment is written. It rolls at segment.bytes (1 GB) or segment.ms. Retention deletes whole closed segments, which is why it is cheap.

Why it is fast. Writes are appends, so the disk sees sequential I/O. Kafka does not fsync each write and does not keep its own cache. It writes into the OS page cache and depends on replication for durability, so a recent write that a consumer reads back is served from RAM. To serve a fetch, the broker finds the segment, binary-searches the sparse index, scans forward a little, then calls sendfile(): bytes go from page cache to the socket without entering user space (zero-copy). Batches are stored in the same format producers send, so the broker never re-encodes them. With TLS that zero-copy path is lost, because encryption runs in user space.

Write path, step by step:

  1. The producer serializes key and value. The partitioner picks a partition: murmur2(key) mod partition count when there is a key. With no key, the sticky partitioner fills one batch per partition, then moves on.
  2. Records accumulate in a per-partition batch until linger.ms or batch.size is reached. The batch is compressed and sent to that partition's leader, which the producer finds from cached metadata.
  3. The leader appends the batch to its active segment in the page cache.
  4. Followers send fetch requests to the leader and append the same bytes. The ISR (in-sync replicas) is the set of replicas that have caught up within replica.lag.time.max.ms (30 s). The high watermark is the highest offset every ISR member has. Consumers can read only up to it.
  5. The ack depends on acks. With 0 the producer does not wait. With 1 the leader acks once it has appended, so a leader crash before replication loses the record. With all (-1) the leader waits until every current ISR member has the record. If the ISR is smaller than min.insync.replicas, the write is rejected with NotEnoughReplicas. That is how RF=3, min.insync=2, acks=all survives one broker failure without losing acked writes.
  6. If a leader dies, the controller elects a new one from the ISR. unclean.leader.election.enable=false (the default) keeps the partition offline rather than electing an out-of-sync replica. That choice is availability versus losing acknowledged data.

KRaft. Cluster metadata (topics, partitions, leaders, ISR) used to live in ZooKeeper. In KRaft it is a Raft-replicated internal log, __cluster_metadata, run by a controller quorum, and brokers follow that log. Kafka 4.x supports only KRaft. Loom's compose runs apache/kafka:4.3.1 as one node with KAFKA_PROCESS_ROLES: broker,controller and a single voter (1@kafka:29093).

Read path and groups:

  1. A consumer with a group.id finds its group coordinator (the broker that leads that group's partition of __consumer_offsets) and joins the group. In the classic protocol one member (the group leader) computes the assignment and the coordinator distributes it. In KIP-848 (the new protocol, GA in 4.0) the broker computes it. Each partition goes to exactly one member, so members beyond the partition count sit idle.
  2. The consumer fetches from its partitions, starting at the committed offset. With no committed offset it uses auto.offset.reset (earliest or latest).
  3. It processes records and commits an offset, meaning "next offset to read", to __consumer_offsets, which is a compacted topic. Auto-commit (enable.auto.commit, every 5 s, done inside poll) can commit records your code has not finished, which loses them if you crash. Commit-before-processing gives at-most-once. Commit-after gives at-least-once, so duplicates follow a crash and your processing must be idempotent.
  4. Liveness uses two clocks. Heartbeats (a background thread in the Java client) must arrive within session.timeout.ms (45 s default), which detects a dead process. Calls to poll() must come within max.poll.interval.ms (5 min), which detects a stuck processing loop. Missing either triggers a rebalance.
  5. Eager rebalancing revokes every partition from every member, then reassigns, so the whole group pauses. Cooperative-sticky moves only the partitions that must move, over two rounds, while the others keep consuming. franz-go, which Loom's Go service uses, defaults to cooperative-sticky.

Retention vs compaction. cleanup.policy=delete drops segments older than retention.ms or beyond retention.bytes. compact keeps at least the latest record per key, and a null value (a tombstone) eventually removes the key. Compaction suits changelogs ("current state of user 42"). Delete suits event streams.

Lag is log-end offset minus committed offset, per partition. Rising lag means consumers are slower than producers. Lag that holds steady and is non-zero is normal. Alert on lag growth or on time-lag, not on a fixed number.

Idempotent producer. The broker gives the producer a PID, and every batch carries a per-partition sequence number. If a retry resends a batch the leader already wrote, the leader sees the duplicate sequence and drops it. That removes duplicates caused by retries, and with up to 5 in-flight requests it also keeps order. Transactions (transactional.id) let one producer write to several partitions and commit consumer offsets (sendOffsetsToTransaction) atomically. Consumers using isolation.level=read_committed skip aborted data. This is "exactly-once" only for read-from-Kafka, write-to-Kafka. An email sent or a DB row written in the middle is outside the transaction and can still happen twice.

4. What can go wrong

Scenario: acks=1 with RF=3, and the leader crashes right after acking.

What actually happens: Followers had not fetched the record. A follower becomes leader, and the acked record is gone. The producer already reported success.

Fix / mitigation: Use acks=all with min.insync.replicas=2 on RF=3, and keep unclean leader election off.

Scenario: A consumer's processing of one batch takes longer than max.poll.interval.ms (a slow downstream API).

What actually happens: The Java client leaves the group and its partitions are reassigned. Its later commit fails (CommitFailedException), the new owner reprocesses the same records, and the cycle repeats as a rebalance storm.

Fix / mitigation: Use smaller max.poll.records, process on a separate pool with pause/resume, or raise the interval. Use cooperative-sticky so rebalances do not stop the whole group.

Scenario: A malformed record (a poison message) makes the handler throw every time.

What actually happens: If you only commit after success, the partition is stuck at that offset forever and lag climbs while every other partition is fine.

Fix / mitigation: Catch the error, publish the raw record and the error to a DLQ topic (or retry topics with backoff), commit, and move on. Alert on DLQ rate.

Scenario: You increase a topic from 6 to 12 partitions.

What actually happens: hash(key) % 12 differs from % 6, so new records for an existing key land on a different partition from its old ones. Per-key order across the change is no longer guaranteed.

Fix / mitigation: Over-provision partitions up front, drain before changing, or make consumers order by a sequence number (as Loom's client does).

5. How it scales

The unit of parallelism is the partition. Producers spread across partition leaders on different brokers. A consumer group can use at most as many consumers as there are partitions. More brokers add disk, network and leader capacity. More consumers help only up to the partition count, and they do not speed up a single hot key, because all of its records are on one partition consumed by one member. Too many partitions cost you: more open files, slower leader failover, longer rebalances. The real bottlenecks are usually a hot key, a slow consumer (watch lag), or cross-AZ replication bandwidth. You scale reads that need full fan-out with more consumer groups, not more members of one group.

Interview questions

Why is Kafka fast when it writes everything to disk?
Disk is slow only for random access. Kafka appends to the active segment of a partition, so writes are sequential, and it writes into the OS page cache instead of fsyncing each record, relying on replication for durability. Reads of recent data are usually served from that same page cache. On a fetch the broker finds the offset using a sparse index and hands the bytes to the socket with sendfile, so data never enters the JVM heap. Producers batch and compress, and the broker stores batches in the same format it receives them, so it never re-encodes. Retention deletes whole segment files, not rows. The caveat is TLS: encryption happens in user space, so you lose zero-copy and pay CPU.
How does Kafka guarantee ordering, and how does Loom rely on it?
Kafka orders records only within a partition. Offsets increase monotonically per partition, and one consumer in a group owns a partition at a time. Across partitions there is no order at all. To keep related events in order, you give them the same key: the default partitioner hashes the key with murmur2 mod the partition count, so they land on one partition. Loom keys every record by runId, so one run's events stay ordered among the six partitions, while different runs interleave freely, which is fine. The idempotent producer keeps order across retries with up to five in-flight requests. Loom does not depend only on Kafka for order, though: every envelope carries a monotonic sequence, and the browser applies lastApplied + 1 and buffers anything ahead of it.
At-most-once, at-least-once, exactly-once: how do you get each?
It comes down to when you commit relative to the side effect. Commit, then process: a crash after the commit skips the record, so at-most-once. Process, then commit: a crash before the commit redelivers it, so at-least-once, and processing must be idempotent. Kafka's exactly-once is the idempotent producer plus transactions: consume, produce outputs, and commit the input offsets in one transaction, with downstream readers on read_committed. That only covers Kafka-to-Kafka. If processing calls Stripe or writes Postgres, you are back to at-least-once plus deduplication, such as an idempotency key or a unique constraint on an event id. Loom's Go consumer commits after processing, so it is at-least-once, and the effect is exactly-once because Redis and the browser both dedupe by sequence.
Walk me through a consumer group rebalance.
A rebalance starts when a member joins, leaves, misses heartbeats past session.timeout.ms, or fails to poll within max.poll.interval.ms, or when the subscribed partitions change. In the classic protocol every member sends JoinGroup to the coordinator, one is elected leader and computes the assignment, and SyncGroup distributes it. With the eager protocol everyone first revokes all partitions, so the whole group stops, and uncommitted work is redone by the new owner. Cooperative-sticky revokes only the partitions that must move, in a second round, so the rest keep flowing. The new KIP-848 protocol moves assignment to the broker and makes it incremental by default. To limit the damage, commit in the revoke callback, use static membership (group.instance.id) for rolling restarts, and keep processing per poll bounded.
What do acks=all and min.insync.replicas actually guarantee?
With acks=all the leader responds only after every replica currently in the ISR has the record. That alone is weak, because the ISR can shrink to just the leader, and then "all" means one copy. min.insync.replicas sets a floor: if the ISR is smaller, the leader rejects the write with NotEnoughReplicas. RF=3 with min.insync=2 means every acked write is on at least two brokers, so losing any one broker loses no acked data. If two are down, writes fail rather than become unsafe, while reads continue. Add unclean leader election off, so a stale replica never becomes leader. Loom runs RF=1 locally, so acks: -1 there means only "the single leader wrote it".
Follow-up: in Loom, what happens if Kafka is down for ten minutes mid-run?
The run keeps going and stays correct, because Redis is written first and is the source of truth. Each publishSwarmEvent eventually throws and bus.ts logs and swallows it. But the Kafka await is on the same serial promise chain as the Redis writes, and kafkajs retries an idempotent producer a very long time by default, so later events reach Redis late and the SSE lane stalls. The Go service's ping fails, consumerUp goes false, /healthz returns 503 and gRPC health reports NOT_SERVING. Sockets go silent, and the browser's gate replays from Redis when it switches lanes. The fix I'd make is to take the Kafka publish off the critical path, or write to an outbox in Redis and relay asynchronously.
Follow-up: why commit a record you couldn't parse?
If I didn't, the offset could never move past it. Each poll would fetch the same bad record again, that partition would block forever, and lag would grow for every run hashed there. In consume() an invalid envelope increments invalidEvents, is logged with partition and offset, and is still added to the batch passed to CommitRecords. That is fine for a telemetry mirror, because the event is also in Redis. For a consumer whose job is the side effect, I'd publish the raw bytes plus the error to a dead-letter topic before committing, alert on that topic's rate, and have a tool to re-drive it after a fix.
Follow-up: your code comment says a stalled poll loop forces a rebalance. True?
It's true for the Java client: if you don't call poll within max.poll.interval.ms, the client leaves the group. franz-go heartbeats from its own goroutine and Loom doesn't enable BlockRebalanceOnPoll, so a stalled loop in Loom mostly means fetches stop, offsets stop being committed, and lag grows. The group stays stable. The design point holds either way: hub.publish must never block, because one frozen subscriber would stop telemetry for everyone. So each subscriber gets a 256-slot buffered channel and is evicted when it's full.
Follow-up: how would you get both Redis and Kafka to agree without a distributed transaction?
Use a transactional outbox. The write that must be durable (here, the Lua script that appends to the Redis stream) is the only write on the request path. A separate relay reads that stream from its last cursor and publishes to Kafka with the idempotent producer, keyed by runId, moving its cursor forward only after the ack. A relay crash causes republishing, and consumers already dedupe by runId:sequence, which Loom sends as the eventId header. You get at-least-once into Kafka, no lost events, and no Kafka latency in the run. Two-phase commit across Redis and Kafka isn't available, and you wouldn't want its blocking anyway.

Checklist

gRPC and Protocol Buffers

1. What problem does it solve?

Internal services call each other constantly. With JSON over REST, every team hand-writes clients, guesses at field types, parses text, and invents its own conventions for timeouts, errors and streaming. gRPC gives you a single schema (.proto) that generates typed clients and servers in many languages, plus a compact binary encoding. It runs over HTTP/2, which multiplexes many calls on one connection and supports streaming natively. Deadlines, cancellation, status codes, health checks and metadata are standardized, so a Go server and a Java client agree on all of them without negotiation.

2. How it works internally

Protobuf encoding. A message is a sequence of (tag, value) pairs. Field names never go on the wire. The tag is a varint equal to field_number << 3 | wire_type. The wire types are 0 VARINT (int32, int64, bool, enum), 1 I64 (fixed64, double), 2 LEN (string, bytes, nested messages, packed repeated) and 5 I32. A varint stores 7 bits per byte, low bits first, and the top bit means "more bytes follow", so small numbers take one byte. A negative int64 always takes 10 bytes, which is why sint64 uses zigzag encoding (-1 becomes 1, 1 becomes 2). Field numbers 1-15 fit in a one-byte tag, so give them to hot fields.

 RunEvent{version:1, run_id:"r1", sequence:3}  (rest = proto3 default)

 08 01        tag 0x08 = field 1 << 3 | 0 (VARINT)  value 1
 12 02 72 31  tag 0x12 = field 2 << 3 | 2 (LEN)  len 2  "r1"
 18 03        tag 0x18 = field 3 << 3 | 0 (VARINT)  value 3
 (occurred_at_ms, kind, payload_json = 0 / "" so not sent at all)

 gRPC message frame on an HTTP/2 DATA frame:
 +------+-------------------+----------------------+
 | 0x00 | 00 00 00 08 (len) | 08 01 12 02 72 31 .. |
 +------+-------------------+----------------------+
  compressed?  4-byte big-endian length   protobuf bytes

The decoder reads a tag. If it knows the field number, it decodes the value into that field. If it does not, it can still skip the value correctly, because the wire type says how long it is, and modern runtimes keep these unknown fields and write them out again on re-serialize. That is how an old service passes newer fields through untouched. It is also why you never reuse a field number: an old binary will decode the new field's bytes as the old field, with the old meaning and possibly a different type, and that corruption is silent. Retire numbers and names with reserved 7; reserved "old_name";. In proto3 a scalar at its default value is not sent and has no presence unless you mark it optional. Loom relies on that: an empty run_id means "every run".

Code generation. protoc with protoc-gen-go generates message structs and marshaling (telemetry.pb.go). protoc-gen-go-grpc generates the client stub, the server interface, a ServiceDesc (method names mapped to handlers) and an Unimplemented...Server struct. Your server embeds that struct, so adding an RPC to the proto does not break compilation, and the new method returns UNIMPLEMENTED until you write it.

One call on the wire:

  1. The client opens (or reuses) one TCP plus TLS plus HTTP/2 connection. Every call is a new HTTP/2 stream on it, with its own odd-numbered stream id, so thousands of calls share a connection without head-of-line blocking at the HTTP layer. TCP-level head-of-line blocking still exists.
  2. The request HEADERS frame carries :method POST, :path /loom.telemetry.v1.TelemetryService/StreamRunEvents, content-type: application/grpc, te: trailers, and grpc-timeout: 9987m if the client has a deadline. Custom metadata goes in as extra headers.
  3. DATA frames carry length-prefixed messages: 1 byte compressed flag, 4 bytes length, then the protobuf bytes. Message boundaries do not have to line up with frame boundaries. HTTP/2 flow control (per stream and per connection windows) provides backpressure: a client that stops reading eventually blocks the server's Send.
  4. The server responds with HEADERS (:status 200), zero or more DATA frames with messages, and then trailers: a final HEADERS frame with grpc-status, grpc-message and END_STREAM. HTTP 200 does not mean success. Only grpc-status: 0 means OK.
  5. Four kinds: unary (one request, one response), server-streaming (one request, many responses, Loom's StreamRunEvents), client-streaming (many requests, one response, for example an upload) and bidi (both directions independent, for example chat or reflection). On the wire they are identical; they differ only in how many messages flow each way before END_STREAM.
  6. Deadline: an absolute point in time ("finish by 12:00:05.000"). A timeout is a relative duration for one hop. gRPC sends the remaining time as grpc-timeout. The server turns it into a context deadline, and if the server passes that ctx into its own outgoing calls, they inherit the shrinking budget. That is deadline propagation. When the deadline passes, both sides give up with DEADLINE_EXCEEDED.
  7. Cancellation: the client cancels its ctx (the user left, or a parent request ended), the library sends RST_STREAM(CANCEL), and the server's ctx.Done() fires. A handler that selects on it stops work immediately. A handler that ignores it keeps burning CPU on behalf of nobody.
  8. Keepalive: HTTP/2 PING frames detect dead connections behind NATs and load balancers. The server's enforcement policy sets how often clients may ping. A client that pings more often gets GOAWAY with too_many_pings and its connection closed.

Status codes and retries. Generally safe to retry with backoff: UNAVAILABLE (server down, connection reset, or Loom's eviction) and RESOURCE_EXHAUSTED (with backoff, if quota resets). Retry DEADLINE_EXCEEDED and ABORTED only if the operation is idempotent, because the server may have done the work. Never blindly retry INVALID_ARGUMENT, NOT_FOUND, ALREADY_EXISTS, PERMISSION_DENIED, UNAUTHENTICATED, FAILED_PRECONDITION, UNIMPLEMENTED or INTERNAL: the same request will fail the same way. gRPC supports declarative retry policies in service config, but you still need a retry budget so retries do not amplify an outage.

Health and reflection. grpc.health.v1.Health has Check (unary) and Watch (server stream). It answers SERVING or NOT_SERVING per service name, where the empty name means the whole server. Kubernetes gRPC probes, grpc_health_probe and Envoy speak it. Reflection (grpc.reflection.v1.ServerReflection, a bidi stream) returns the server's file descriptors, so grpcurl can list services and call methods without the .proto file.

4. What can go wrong

Scenario: You put 3 gRPC server pods behind an L4 (TCP) load balancer and add 3 more under load.

What actually happens: Each client opened one HTTP/2 connection at startup, the LB pinned it to one pod, and every later call is multiplexed on that connection. The new pods get no traffic and the old ones stay hot.

Fix / mitigation: Use client-side balancing (round_robin over a headless-service DNS name or xDS), or an L7 proxy (Envoy, Linkerd, a service mesh) that balances per request. Set server MaxConnectionAge so clients reconnect and re-resolve.

Scenario: A caller sets no deadline and the downstream hangs.

What actually happens: The call waits forever, goroutines and connections pile up, and the upstream request that triggered it has long since timed out. Its work is wasted and it holds resources.

Fix / mitigation: Every outgoing call gets a deadline derived from the incoming ctx, and handlers select on ctx.Done().

Scenario: Someone deletes field 4 and later adds string region = 4;.

What actually happens: Old clients still send field 4 as an int64 varint. New servers read that tag with a wire-type mismatch and treat it as an unknown field or a parse error, while old servers misread new data. Stored payloads are now ambiguous.

Fix / mitigation: reserved 4; on deletion, add new fields with new numbers only, and run a breaking-change linter (buf breaking) in CI.

Scenario: A streaming client sends keepalive pings every 5 s.

What actually happens: The server's enforcement policy (MinTime) is violated, so the server sends GOAWAY too_many_pings and drops the connection, and long streams die at random.

Fix / mitigation: Align the client keepalive Time with the server's MinTime. Loom permits 15 s.

5. How it scales

Each connection carries many concurrent streams, bounded by MaxConcurrentStreams (often 100 by default on the client's view of the server). The usual bottleneck is uneven load caused by connection pinning, not raw throughput. More server instances help only once the balancing is per request or per stream. For long-lived server streams like StreamRunEvents, each subscriber holds one stream and one goroutine plus a buffer, so memory per subscriber is the limit. Rebalancing existing streams onto new pods also requires the streams to end, which is what MaxConnectionAge with graceful GOAWAY does. Adding replicas does not help a stateful fan-out like Loom's hub unless every replica sees every event, which comes down to the Kafka consumer-group design.

Interview questions

gRPC vs REST: when would you pick which?
For internal service-to-service calls I'd use gRPC. The .proto file is the contract and generates typed clients in every language, protobuf is smaller and faster to parse than JSON, HTTP/2 multiplexes calls on one connection, and you get all four streaming modes plus standard deadlines, cancellation and status codes. For public APIs and browsers I'd use REST with JSON: anyone can call it with curl, HTTP caches and CDNs understand it, and browsers support it natively. Browsers cannot speak native gRPC because they don't expose trailers or HTTP/2 framing, so you'd need gRPC-Web and a proxy. Loom does exactly this split: Next.js routes are REST and SSE for the browser, the Go service exposes gRPC for services, and a WebSocket carries the same feed to browsers.
What are the four kinds of RPC, and which does Loom use?
Unary is one request and one response, a normal function call. Server streaming is one request followed by a stream of responses, for subscriptions or large result sets. Client streaming is a stream of requests and then one response, for uploads or aggregation. Bidirectional streaming has two independent streams, for chat or interactive protocols. On the wire they are the same: one HTTP/2 stream, length-prefixed messages in DATA frames, trailers at the end. They differ only in how many messages each side sends before closing. Loom has a unary GetRunMetrics for a snapshot and a server-streaming StreamRunEvents, because a subscriber wants pushed events, not polling. Reflection, which Loom registers, is itself a bidi RPC.
How do deadlines propagate across services?
A deadline is an absolute time. The client sets one through its context, and the library sends the remaining time in the grpc-timeout header. The server turns that into a deadline on the handler's context. If the handler passes the same context to its own downstream calls, each one sends a smaller grpc-timeout, so the whole chain shares one budget and nobody keeps working after the original caller has given up. Fixed per-hop timeouts don't compose: five hops with 2 s each can run 10 s after a 3 s caller has already left. When the deadline expires, the client fails with DEADLINE_EXCEEDED and the server's ctx.Done() fires. Loom's stream handler selects on stream.Context().Done(), so a client deadline ends the stream and runs release().
Why can't you load-balance gRPC with a normal TCP load balancer?
An L4 balancer chooses a backend once per TCP connection. gRPC opens one long-lived HTTP/2 connection and multiplexes every call over it, so all of a client's traffic sticks to whichever pod it reached first. Scaling out adds pods that get nothing, and a restart can pile clients onto one pod. You need to balance per request. Either the client does it, with a resolver that returns all pod IPs (a headless Kubernetes service or xDS) and a round_robin policy that keeps a connection to each, or an L7 proxy such as Envoy or a mesh terminates HTTP/2 and spreads individual streams. Add server MaxConnectionAge so connections recycle and pick up new pods.
Walk me through StreamRunEvents from Kafka to the client.
The franz-go poll loop in main.go fetches records from loom.swarm.events. process validates the envelope, increments counters and builds a RunEvent with the raw event JSON in payload_json. hub.publish takes a mutex and does a non-blocking send into every matching subscriber channel, which has 256 slots. A full channel is closed and the subscriber evicted, so the Kafka loop never waits. Then offsets are committed. The handler had called subscribe(runId) and is selecting on its channel and on stream.Context().Done(). Each event becomes stream.Send: a 5-byte-prefixed protobuf message in an HTTP/2 DATA frame. The call ends with trailers: CANCELLED or DEADLINE_EXCEEDED from the client context, or UNAVAILABLE if evicted or shutting down, which means "reconnect and replay from Redis".
Follow-up: why return UNAVAILABLE on eviction rather than just skipping events?
Skipping would leave a silent hole. The client would never know sequence 42 was missing unless it checked. Closing the stream with a retryable status is loud and honest: the client knows its view is incomplete, reconnects, and replays from the durable log, a recovery path that already exists. UNAVAILABLE is the right code because retrying will probably work. INTERNAL would wrongly suggest a bug, and RESOURCE_EXHAUSTED suggests a quota. Eviction also frees the goroutine and buffer right away. Blocking instead would let one slow subscriber stall the Kafka loop and everyone else's feed.
Follow-up: how do you evolve a proto without breaking clients?
Add fields with new numbers. Old readers skip them as unknown fields and keep them, and new readers see defaults when old writers omit them. Never change a field's number or its wire-incompatible type, and never reuse a number or name: mark deleted ones reserved. Renaming a field is wire-safe, because names aren't on the wire, but it breaks JSON mapping and generated code. Changing int32 to int64 is wire-compatible but can truncate in old readers. Don't change a field into or out of a oneof casually. Add RPCs freely, because servers embed Unimplemented...Server. For a breaking change, publish v2 as a new package next to v1. That is why Loom's package is loom.telemetry.v1. Run buf breaking in CI to enforce all of this.
Follow-up: why does Loom close the hub before GracefulStop?
GracefulStop stops accepting new RPCs and then waits for every in-flight RPC to return. A server-streaming handler like StreamRunEvents loops until its channel closes or the client leaves, so on its own it would never return, and shutdown would hang until the orchestrator killed the process. Calling events.closeAll() first closes every subscriber channel, each handler sees !open and returns UNAVAILABLE, and then GracefulStop finishes. The bufconn test cleanup checks this: it cancels the server context and fails if serveGRPCOn hasn't returned within 5 seconds.
Follow-up: what does bufconn buy you over a real port, and what doesn't it test?
bufconn is an in-memory net.Listener from grpc-go. The test runs the real server (registration, interceptors, health, streaming and shutdown) and a real client over full HTTP/2 framing, with no port binding, so tests are fast, parallel-safe and not flaky on CI. Loom dials it with passthrough:/// and a context dialer so the client skips DNS. It doesn't test real network behavior: TLS, TCP keepalive against a NAT, load balancer behavior, or real latency and packet loss. Those need an integration test against the container. It also doesn't exercise Kafka, so the tests inject events directly with hub.publish.

The WebSocket protocol, with SSE and long polling

1. What problem does it solve?

HTTP cannot speak until asked. A WebSocket turns one TCP connection into a full-duplex message channel with 2 to 14 bytes of framing per message.

2. How it works internally

  1. Client sends a normal GET with Upgrade: websocket, Connection: Upgrade, Sec-WebSocket-Version: 13, Origin and Sec-WebSocket-Key (16 random bytes, base64).
  2. Server answers 101 Switching Protocols with Sec-WebSocket-Accept = base64(SHA-1(key + fixed GUID)). This proves the server really speaks WebSocket and is not a cache replaying a response. It is not authentication.
  3. From then on the socket carries frames. A message is one or more frames; the last has FIN=1. Opcodes: 0x0 continuation, 0x1 text, 0x2 binary, 0x8 close, 0x9 ping, 0xA pong.
  4. Client-to-server frames are XOR-masked with a fresh 4-byte key; server frames never are. Masking stops page JavaScript from putting predictable bytes on the wire that a broken proxy could parse as HTTP and cache. It is not encryption.
  5. Control frames are at most 125 bytes, never fragmented, and may sit between fragments of a large message. A ping must get a pong with the same payload; browsers answer automatically but their JS API cannot send pings.
  6. Close is a handshake: send a close frame (code + reason), the peer echoes it, the server closes TCP. 1000 normal, 1001 going away, 1008 policy violation, 1013 try again later. 1006 is never sent: the browser reports it when TCP died with no close frame.
  7. Heartbeats: a sleeping laptop or expired NAT entry leaves a half-open connection that TCP keepalive (about 2 hours by default) will not notice. The server pings on a timer and closes the connection if no pong arrives.

Socket.IO and delivery guarantees (ChatFlow)

1. What problem does it solve?

Raw WebSocket gives frames. Chat also needs named events, rooms, acks, reconnection, a fallback when WebSocket is blocked, and broadcasts across processes. Socket.IO is its own protocol: a plain WebSocket client cannot talk to it.

2. How it works internally

  1. Engine.IO handshake. By default GET /socket.io/?EIO=4&transport=polling returns the open packet 0{"sid","upgrades":["websocket"],"pingInterval","pingTimeout","maxPayload"}. Packet types: 0 open, 1 close, 2 ping, 3 pong, 4 message, 5 upgrade, 6 noop.
  2. Upgrade. The client opens a WebSocket with the same sid, sends 2probe, gets 3probe, pauses polling, sends 5. Starting on polling guarantees a connection even where WebSocket is blocked.
  3. Heartbeat (EIO v4). The server sends 2 every pingInterval; no 3 within pingTimeout and it closes the socket. The client treats silence longer than pingInterval + pingTimeout as dead.
  4. Socket.IO packets ride inside Engine.IO messages: 0 CONNECT, 1 DISCONNECT, 2 EVENT, 3 ACK, 4 CONNECT_ERROR, 5/6 binary. 42["message:new",{...}] is message + event; 4217[...] wants ack 17, answered by 4317[...].
  5. Namespaces multiplex logical channels with their own middleware. Rooms are server-only: the adapter holds Map<room, Set<socketId>> in that process's memory.
  6. Auth. auth: { token } travels in the CONNECT packet; middleware reads socket.handshake.auth and calls next() or next(err), which becomes CONNECT_ERROR and a client connect_error. It runs once per connection.
  7. Reconnect. The client retries with backoff and jitter and buffers emits made while offline. Server emits to a disconnected socket are lost, and the new socket has a new id and no rooms until you rejoin.
  8. Multiple nodes. Polling is many HTTP requests; each must hit the process holding that sid, or you get "Session ID unknown": hence sticky sessions. A WebSocket is one TCP stream and is pinned naturally. io.to(room).emit reaches local sockets only; the Redis adapter publishes each broadcast to Redis pub/sub and every node delivers to its local members.

Delivery. Default is at-most-once; a volatile emit is discarded if the transport is not writable at that moment (right for typing indicators). At-least-once with an exactly-once effect: the client sends its own message id; the server persists under a unique constraint and acks only after commit; the client retries with the same id on ack timeout; the server stamps a per-room sequence; recipients ask for "everything after N" on reconnect or gap and drop anything at or below N. Socket.IO 4.6+ connectionStateRecovery replays short disconnects from memory, not from a durable log.

Interview questions

How is a WebSocket connection established?
It starts as an HTTP GET with Upgrade: websocket, Connection: Upgrade, version 13 and a random base64 Sec-WebSocket-Key. The server appends a fixed GUID to the key, SHA-1 hashes and base64-encodes it, and returns that as Sec-WebSocket-Accept with a 101. That proves the server understood the upgrade; it is not security. After that the TCP connection carries frames: FIN, opcode, mask bit, length, payload. Because that GET is the only HTTP moment, the Origin check and authentication have to happen there.
How is Socket.IO different from WebSockets?
It is a protocol on top of transports. Engine.IO opens with long polling by default, upgrades to WebSocket with a probe, and runs its own ping/pong. Socket.IO adds named events, namespaces, server-side rooms, acks with ids, reconnection with backoff, offline emit buffering and adapters for multi-node broadcast. Costs: a plain WebSocket client cannot connect, polling needs sticky sessions, and delivery is still at-most-once. In ChatFlow rooms map one-to-one onto groups, and typed event maps catch payload mistakes at compile time.
Trace a ChatFlow message from sender to recipient.

Persist then broadcast, or the reverse?
Persist first. Broadcasting first means a failed INSERT shows people a message that vanishes on reload. Persisting first also gives a database id and timestamp to send, which recipients use for ordering and de-duplication. The cost is the INSERT on the latency path, and ChatFlow still measured p50 6 ms end to end at 1,000 sockets. If the broadcast fails after commit nothing is lost: the client recovers it by fetching after its last id. ChatFlow persists first on both the socket and REST paths.
How do you authenticate a socket, and what about token expiry?

How would you run ChatFlow on three nodes?
Three changes. Broadcasts: add the Redis adapter so each node publishes broadcasts and every node delivers to its local room members. Presence: onlineUsers is a per-process map, so move it to Redis sets with expiry for crashed nodes. Routing: sticky sessions if polling is ever enabled, because a sid's buffered state lives in one process. My load test put the single-process ceiling at about 97k deliveries/s, bound by one CPU core, so this also buys throughput, until Postgres INSERTs or Redis fan-out become the limit.
Follow-up: How do you get at-least-once without duplicates?
Make a durable log the truth and the socket a hint. The client tags each send with its own id and keeps it pending until acked. The server assigns a per-room sequence; recipients track the last applied, and a gap or reconnect triggers "everything after N"; anything at or below N is dropped. Follow-up: What is bufferedAmount, and what do you do with slow consumers?

Checklist

The Go runtime and concurrency primitives

1. What problem does it solve?

You want one goroutine per connection, the simplest code, without one OS thread per connection with megabyte stacks and kernel context switches. Go multiplexes many goroutines onto few threads in user space.

2. How it works internally

  1. G, M, P. G is a goroutine (stack starts at a few KB, grows by copying). M is an OS thread. P is a scheduling context with a local run queue (256 slots plus runnext); there are GOMAXPROCS Ps, by default usable CPUs (respecting container CPU limits since Go 1.25). An M needs a P to run Go code.
  2. Scheduling. go f() puts the new G in the current P's runnext. An M runs its P's local queue, checks the global queue every 61st tick for fairness, then the netpoller, and when idle steals half of another P's queue.
  3. Preemption. Cooperative at function prologues; since Go 1.14 sysmon also signals a goroutine running over about 10 ms, so tight loops cannot hog a P.
  4. Blocking syscalls (file I/O, cgo) pin the M; its P is handed to another M so other goroutines keep running. When the call returns, the G needs a P again or goes to the global queue.
  5. Netpoller. Sockets are non-blocking. A goroutine reading an empty socket parks; the fd sits in epoll/kqueue; readiness makes the goroutine runnable again. Idle WebSockets cost parked Gs, not threads.
  6. Channels. Unbuffered send blocks until a receiver takes it (handoff). Buffered send blocks only when full. After close, receivers drain the buffer, then get the zero value with ok == false. Sending on closed, closing twice, or closing nil panics. A nil channel blocks forever, so a nil case in select is disabled.
  7. select picks randomly among ready cases; with none ready, default runs. select { case ch <- v: default: } is a send that can never block.

Backpressure: Loom's telemetry fan-out hub

1. What problem does it solve?

One Kafka consumer feeds N readers (browsers over WebSocket, gRPC streams) at different speeds. If the producer waits for the slowest, one frozen tab stalls everyone and stops offset commits. Backpressure means deciding where waiting stops.

2. How it works internally

  1. Registry. hub{ mu sync.Mutex; nextID uint64; subscribers map[uint64]*subscriber; active, dropped atomic.Int64 }; each subscriber{ runID string; events chan *RunEvent } is buffered to subscriberBuffer = 256. Empty runID means all runs.
  2. subscribe makes the channel, locks, takes nextID++, inserts, unlocks, and returns a receive-only channel and release. Release runs in sync.Once and closes only if the id is still registered: closed exactly once, by release or eviction.
  3. Producer. consume (main.go) is one goroutine: PollFetches (franz-go, DisableAutoCommit); per record process then hub.publish; then CommitRecords for the batch. Invalid records are committed too, so a poison message cannot pin a partition.
  4. publish locks and walks all subscribers, skipping other runs, doing select { case sub.events <- event: default: evict }. Holding the lock across sends is safe only because no send can block: the critical section is bounded by subscriber count, not reader speed.
  5. Eviction: delete, close(sub.events), dropped.Add(1), update active, log. The whole subscriber goes, not one event: a skipped event is a silent hole, a closed stream is loud.
  6. Downstream. The WebSocket goroutine still receives the buffered events (the hub test drains exactly 256), then sees open == false and closes with 1013 "subscriber fell behind". gRPC returns codes.Unavailable. Each WebSocket write also has a 5 s deadline, so a stalled TCP send cannot hold its goroutine.
  7. Client recovery (wsTransport.ts, runStream.ts): onclose calls retire, which reports onDown at once; rendering switches to the SSE lane and gate.resync() fetches GET /api/swarm/[runId]?after=lastApplied from the Redis stream (pages of 1,000, max 20). The socket reconnects with backoff; when it opens it takes over and replays again, because the hub only forwards events published after subscribing.

Interview questions

Explain Loom's hub: what happens when one subscriber is slow?
The hub is a map from id to subscriber behind a mutex; each subscriber has a channel buffered to 256 and an optional run filter. The single Kafka poll goroutine calls publish per record. It locks and, for each matching subscriber, does a select with default: room means the event goes in; full means delete from the map, close the channel, bump the dropped counter. The slow one is gone in that same call and nobody else notices. Its WebSocket goroutine drains the buffer, sees the closed channel, closes with 1013, and the browser falls back to SSE and replays from Redis.
Why not block, or drop just the one event?
Blocking lets the slowest client set everyone's pace: the poll loop stops, commits stop, lag grows, and since publish holds the lock, subscribe and release hang too. With a Java-style consumer you eventually leave the group and trigger a rebalance. Dropping one event is a silent hole; Loom's client would replay on a sequence gap, but a dropped final event leaves no gap to see. Eviction is loud, frees memory at once, and reuses a recovery path that already exists: replay from Redis by sequence.
Buffered vs unbuffered channels, and close semantics?
An unbuffered send completes only when a receiver takes the value, so it synchronises. Capacity C lets C sends finish without a receiver, then blocks. Close means done: receivers drain the buffer, then get zero with ok == false, which ends for range. Send on closed, double close and close of nil all panic; a nil channel blocks forever, handy for disabling a select case. In the hub, close is the single "subscription over" signal, so it happens exactly once, under the lock, with sync.Once on release.
How does the Go scheduler work?
It is M:N. Goroutines (G) run on OS threads (M) that must hold one of GOMAXPROCS processors (P). Each P has a local run queue, plus a global queue checked periodically for fairness; an idle P steals half of another's queue. Preemption is cooperative at function calls and, since 1.14, signal-based for goroutines running more than about 10 ms. A blocking syscall hands its P to another thread. Network I/O never blocks a thread: the goroutine parks and the netpoller wakes it when epoll says ready. That is why a goroutine per WebSocket is cheap.
Data race vs race condition; what does -race prove?
A data race is two goroutines touching the same memory concurrently, at least one writing, with no happens-before between them: torn values, stale reads, corrupted maps. A race condition is a logic bug that depends on interleaving and can exist with every access locked, like check-then-act across two critical sections. -race compiles in ThreadSanitizer: every memory access is instrumented, and vector clocks updated by channels, locks, atomics and WaitGroups track happens-before; unordered conflicting accesses are reported. It costs about 2 to 20 times CPU and 5 to 10 times memory, catches only races on paths that ran, and never logic races. Evidence, not proof.
Follow-up: Can publish deadlock?
Deadlock needs someone holding a lock while waiting on something that needs that lock released. Under mu, publish does only map edits, non-blocking sends, closes and atomic stores, so it always releases in bounded time; release takes the same lock and never waits on a channel. The real cost is contention: the lock is held for O(subscribers) per event, so at high rates subscribe and release queue behind it. Counters are atomics precisely so /metrics and GetRunMetrics never touch the lock.
Follow-up: What does an evicted browser see, and can it miss or duplicate events?
Up to 256 buffered frames, then a 1013 close. The client does not check the code: onclose retires the socket, rendering switches to the SSE lane it was draining all along, and resync fetches everything after lastApplied from Redis. The gate applies only lastApplied + 1, parks anything ahead, drops anything at or below, so overlap between lanes cannot double-apply persisted events; sequence-0 frames bypass it. Known edge: the end-of-run replay stops after one page when nothing is parked, so a gap over 1,000 events could lose run.done.

Timeouts, retries and idempotency

1. What problem does it solve?

You cannot tell a slow node from a dead one. Retrying cures transient faults, but retrying something that already happened duplicates its effect.

2. How it works internally

  1. Failure model. Crash-stop, crash-recovery, omission (lost message), timing (too late). Partial failure is normal: some calls succeed, some fail, some are unknown.
  2. A timeout fires. Three worlds look identical: never arrived; still running; done but reply lost. A retry must be safe in the third.
  3. Budgets. One deadline at the edge, the remainder passed down; cancel children when the parent quits.
  4. Backoff. ceiling = min(cap, base * 2^n). Full jitter: random(0, ceiling). Equal jitter: ceiling/2 + random(0, ceiling/2).
  5. Amplification. Three layers retrying 3 times each = 27 calls at the bottom. Retry at one layer, skip non-retryable errors (most 4xx), cap retries at a budget (say 10% of traffic).
  6. Idempotency key. One client UUID per logical operation; the server stores (user, key, request_hash, status, response) under a unique constraint, in the effect's transaction.

Interview questions

How would you make a "create payment" API safe to retry?

The server keeps a table keyed by user and key with the request hash, status and stored response. Same key and hash replays the response; same key with a different body is 422; a repeat while in progress gets 409. Rows expire after a day. That is Stripe's own model.
Explain at-least-once versus exactly-once.
Delivery, processing and commit are separate events. Commit first and a crash loses the message: at-most-once. Process first and a crash redelivers it: at-least-once. Exactly-once delivery over a network isn't achievable in general, but an exactly-once effect is: at-least-once plus an idempotent consumer. Loom does it with sequence numbers: Redis rejects a sequence it already stored, the browser drops anything at or below lastApplied, and gaps are filled from the Redis stream. Kafka's transactional exactly-once only covers consume-transform-produce inside Kafka, not your database.
What is the outbox pattern, and does Loom need one?
Writing your database and publishing to a broker are two operations with no shared transaction, so a crash between them loses or invents an event. The outbox writes the event row in the same transaction as the business change, and a relay or CDC publishes it until acknowledged. Loom does a dual write: Redis first, then Kafka, with Kafka failures swallowed. Since Redis is the source of truth and Kafka only feeds telemetry, that's acceptable, but the serial chain lets a Kafka outage stall Redis. I'd append an outbox entry inside the same Lua script and relay asynchronously.
Follow-up: why full jitter, and what does your code do?
Without jitter, clients that failed together retry together, so recovery traffic arrives as spikes. Full jitter picks uniformly between zero and the exponential ceiling, spreading retries across the whole window; AWS's simulations show it gives the least contention. My WebSocket reconnect uses equal jitter: half the ceiling fixed plus a random half, 500 ms base, 8 s cap, six attempts. That guarantees a minimum wait, but if a Go deploy dropped thousands of tabs at once, full jitter would spread them better.
Follow-up: the Go service crashes after pushing to sockets but before committing. What does the user see?
Nothing wrong. The consumer group resumes from the last committed offset, so the hub pushes those same events again. Each carries its run sequence number, and the browser gate drops anything at or below lastApplied, so nothing is applied twice. What breaks is the metrics: counters such as token chunks are incremented during processing, so a redelivery over-counts them on the Prometheus endpoint. I'd fix that by deduplicating on runId and sequence, or by deriving those numbers from the Redis log instead.
Follow-up: is Loom CP or AP?
CAP only applies during a partition and describes one replicated register, so it's a rough lens. For the run log Loom picks consistency: if Redis is unreachable the route returns 503 rather than start a run it can't record. For Kafka it picks availability: runs proceed and the mirror loses events. PACELC covers the normal case: in direct mode SSE sends an event before Redis confirms it, trading consistency for latency, while Temporal mode reads from Redis and trades latency for consistency.

Temporal and durable workflows

Understand reliability and production systems

Goal: Explain what Temporal persists, why workflows must be deterministic, and what Loom's Temporal path does and does not recover from.

Checklist

Temporal

1. What problem does it solve?

Multi-step processes must survive crashes without a hand-built state machine, queue, timers and retries. Temporal records every decision in a history from which any worker rebuilds state.

2. How it works internally

  1. Parts. The server stores histories and task queues, never running your code; workers long-poll a queue.
  2. Workflow vs activity. The workflow deterministically decides; activities do (HTTP, DB, LLM). History records ActivityTaskScheduled, then ActivityTaskCompleted with the result.
  3. Replay. A worker without cached state re-runs the workflow from the start, matching each command to history; finished activities return recorded results without running. A mismatch raises a non-determinism error, hence no Date.now(), Math.random() or I/O. The TS SDK sandboxes workflows and makes those deterministic; use sleep and patched().
  4. Timeouts. Schedule-to-start: queue wait. Start-to-close: one attempt. Schedule-to-close: all attempts. Heartbeat: max gap between heartbeat() calls; detects dead workers and delivers cancellation.
  5. Retries. Default 1 s, x2, max 100 s, unlimited attempts unless non-retryable. Activities run at least once, so pass an idempotency key (workflow id + activity id) outward.
  6. Signals: recorded async messages in. Queries: unrecorded reads. Updates: recorded synchronous writes.
  7. Worker crash. History, timers and queues survive; the workflow resumes elsewhere by replay; the in-flight activity attempt is retried after its timeout.
  8. Saga. Push each step's compensation; on failure run them in reverse, each idempotent and retried.
  9. DAG. Dependency logic lives in workflow code: compute the ready set, start those activities in parallel; on replay finished tasks resolve from history.

Interview questions

Why can't workflow code call Date.now(), Math.random() or the network?
Temporal doesn't snapshot memory; it rebuilds a workflow by re-running the code against recorded history, and every command issued on replay must match what history says. Read the clock and replay sees a different time, may take another branch, and schedules a different activity, so the worker throws a non-determinism error. A network call also repeats its side effect on every replay. So non-deterministic work goes in activities, whose results are recorded once and read from history afterwards. The TypeScript SDK sandboxes workflows and makes Date and Math.random deterministic.
What survives a worker crash, in general and in Loom?
In general, history, timers, signals and queued tasks live on the server, so the workflow resumes elsewhere by replay, completed activities don't re-run, and the in-flight activity is retried after its heartbeat or start-to-close timeout. In Loom the whole swarm is one activity with maximumAttempts 1, so after the 30-second heartbeat timeout the activity and workflow fail. The Redis events written before the crash survive and replay, but nothing marks the run failed, so it says running until its 24-hour TTL. Temporal gives Loom queueing, not recovery.
How would you redesign Loom on Temporal?
Move orchestration into the workflow and make each model call an activity. The planner activity returns the plan, which history records. The workflow keeps the completed map, calls the existing nextWave function, and starts one activity per ready task in parallel. The revise loop becomes workflow logic over worker and validator activities; synthesis is the last activity. Each activity keys its output by workflow id and task id, stores it in Redis, and returns the stored value if present. Event sequences must come from Redis, not an in-memory counter. Then retries can be enabled.
Follow-up: how is an LLM activity idempotent when its output is random?
Idempotent means a retry has the same effect, not the same text. Make the first successful result authoritative: key it by workflow id and task id, store it before returning, and on retry return the stored one instead of calling the model. Events derived from it use the same key so a retry doesn't emit a second set. You still pay for attempts that crashed before storing; Temporal only promises at-least-once activity execution. Heartbeat details can carry partial progress, such as text streamed so far, into the next attempt.
Follow-up: when would you not use Temporal?
When the job is one short step, a BullMQ or SQS job with retries is enough and needs no new cluster to operate. When work is cheap to restart, direct execution plus a status row is simpler, which honestly describes Loom at six tasks and five minutes. Temporal pays off with many steps that have expensive or external side effects, long waits on humans or timers, and compensation logic: payments, provisioning, onboarding. The cost is a cluster, determinism discipline, and versioning every workflow change.

If bookCar fails with a non-retryable error, it runs the list in reverse: cancel hotel, then cancel flight. Every booking and every compensation is an activity with retries and an idempotency key, because a timed-out booking must not book twice and a failed compensation must be retried until it succeeds. Authentication, authorization and API hardening

1. What problem does it solve?

Authn: who is this? Authz: may they touch this object? Most breaches are authz failures (IDOR).

2. How it works internally

  1. Passwords. Store salt:scrypt(pw, salt). Per-user salt defeats precomputed tables; scrypt needs about 128 * N * r bytes per guess, killing GPU parallelism. A hash has no key to steal. Compare with timingSafeEqual, not ===, which exits at the first differing byte.
  2. JWT. header.payload.signature; HS256 = HMAC-SHA256 with a shared secret; verify recomputes it and checks exp. Proves the key holder issued unexpired claims. Not that the user exists, the role is current, or the token wasn't stolen. Payload is readable. Pin algorithms against alg: none and RS256→HS256 confusion.
  3. Sessions vs JWT. Session id: lookup per request, instant revocation. JWT: no lookup; revocation needs short expiry + refresh, or a denylist.
  4. Zod. Parse unknown into a typed value; unknown keys are stripped (no mass assignment).

Interview questions

What does verifying a JWT prove?
That someone with the key signed it, header and payload weren't changed, and, if checked, it hasn't expired. Not that the user still exists, still has that role, didn't log out, or that the token wasn't stolen. The payload is base64url, readable by anyone. In ChatFlow the role rides in the JWT, so a demotion only takes effect when the 7-day token expires. That's the stateless trade: no lookup, weak revocation. Short access tokens with refresh, or a DB check on privileged routes, fix it.
Why scrypt, why a salt, why not encryption?
Hashes get stolen along with the database, so the aim is to make offline guessing expensive. scrypt is slow and memory-hard: each guess needs megabytes of RAM, which defeats the cheap parallelism GPUs rely on. A random per-user salt means no single precomputed table cracks everyone, and two users with the same password get different hashes. Encryption is reversible, so stealing the key exposes every password; a hash has no key. ChatFlow uses Node's scrypt with a 32-byte salt and compares with timingSafeEqual so timing doesn't leak matching bytes.
What is IDOR and how do your projects prevent it?
The user is authenticated but the handler loads an object by id without checking it is theirs, so editing the id reads someone else's data. The fix is an ownership check on every access in the service layer. Loom's replay route returns 404 unless the run's ownerId is the session user, and the MCP tool does the same; 404 instead of 403 avoids confirming the run exists. ChatFlow calls assertMembership before reading a group or messages, assertGroupAdmin before changing members, and checks membership on socket room:join.
How does Stripe webhook verification work, and how do you handle duplicates and order?
Stripe HMACs the timestamp plus raw body with the endpoint secret. Loom reads the raw bytes, capped at 1 MB, and calls constructEvent before any JSON parsing, because parsing changes bytes. A timestamp outside five minutes is rejected, which stops replaying a captured request later. Stripe delivers at least once and out of order, so in one transaction Loom inserts the event id with ON CONFLICT DO NOTHING, locks the billing row FOR UPDATE, and writes only if the event is newer than last_stripe_event_created, using subscription state re-fetched from Stripe. A 500 rolls back the claim so Stripe's retry is processed.
Follow-up: why doesn't output schema validation stop prompt injection?
The schema checks shape, and injected instructions can produce perfectly shaped output: tell Loom's validator to approve and it can return approved true with score ten, which Zod accepts. Schemas stop malformed output from crashing code; they say nothing about honesty. Defences sit around the model: remove free text where possible, as SoilSense does by sending five cast numbers; label untrusted content; keep decisions in code; and above all limit what output can cause, which is why Loom's MCP tools are read-only.
Follow-up: CORS is configured, so why check Origin too?
CORS is browser-enforced and only decides whether a page may read the response. A cross-site form POST is still sent with cookies, and its side effect happens. That's CSRF. Loom uses session cookies, so hasTrustedOrigin rejects mutations whose Origin, or Referer when Origin is missing, isn't the app's. WebSockets get no preflight, so the Go service checks Origin on the handshake, but it allows an empty Origin, which any non-browser client can send. Hence the socket also needs a token.
Follow-up: rate limiting with three instances, which algorithm and where?
The counter must be shared, or each instance allows the full limit: ChatFlow's in-memory store would triple. Put it in Redis and make check-and-increment atomic with a Lua script, as Loom's run quota does. Loom uses a fixed window, which allows a double burst across the boundary; a token bucket storing tokens and last refill time fixes that and permits controlled bursts. Coarse IP limits belong at the edge, per-user and per-plan limits in the app, and per-dependency limits before expensive calls, like Loom's 120 per hour per model.

1. What problem does it solve?

You want the number of users or messages at which latency stops being acceptable, and the resource that gives out first. Without a load test you learn both from an outage.

2. How it works internally

  1. Closed model (k6 ramping-vus, constant-vus): N virtual users loop "send, wait for response, think". Throughput = N / (R + think). When the server slows, the generator slows too.
  2. Coordinated omission: in that closed loop, during a 2 s stall each VU sends one request instead of the twenty it should have, so the stall shows up as one slow sample, not twenty. Your p99 looks better than real users would see.

Docker and Docker Compose

1. What problem does it solve?

"Works on my machine" comes from different filesystems, library versions and process setups. A container ships the filesystem and the start command together and isolates the process without the cost of a full VM, because it shares the host kernel.

2. How it works internally

  2. Multi-stage: build in a fat stage, copy only artifacts into a small runtime stage. ChatFlow: deps (prod modules), build (tsc + prisma generate), runtime.
  3.   5. Healthcheck: Docker runs the check inside the container every interval; status goes starting → healthy/unhealthy. depends_on: condition: service_healthy delays a dependent's start. Plain Docker does not restart unhealthy containers; orchestrators do.
  6. Stop: docker stop sends SIGTERM to PID 1, waits the grace period (10 s default), then SIGKILL. The kernel gives PID 1 no default signal actions: without a handler, SIGTERM is ignored and you always wait for the kill. Shell-form CMD node x makes /bin/sh PID 1, and it does not forward the signal. Use exec form; add --init/tini if you spawn children (zombie reaping).

Scenario: SIGTERM while sockets are open.

What actually happens: ChatFlow's shutdown() calls server.close(), which waits for open connections. Live WebSockets never close on their own, so it hits the 10 s force-exit, which races Docker's 10 s SIGKILL.

Fix / mitigation: Call io.close() first, the way Loom closes its hub before server.Shutdown; set a longer stop_grace_period.

Scenario: A client inside Compose connects to Kafka.

What actually happens: The broker answers with its advertised address. If that is localhost:9092, the client then connects to itself and fails.

Fix / mitigation: Loom's two listeners: INTERNAL://kafka:19092 for containers, HOST://localhost:9092 for your laptop.

5. How it scales

Stateless containers (API, gateway) scale by running more copies behind a load balancer. Containers with volumes (pgdata, kafka-data) do not: that state needs replication, not copies. Compose is single-host; beyond that you need an orchestrator or a platform like Render.

6. How I used it

ChatFlow: backend/Dockerfile (3 stages, node:22-alpine, non-root uid 1001, exec-form CMD, HEALTHCHECK with wget on /health); docker-compose.yml gates backend on postgres being healthy (pg_isready) and frontend on a healthy backend. backend/src/server.ts handles SIGTERM/SIGINT with a 10 s force-exit.

Interview questions

What is the difference between unit, integration and e2e tests? Which are yours?
A unit test checks one function with no I/O; it runs in milliseconds and pins down logic, like Loom's nextWave scheduler or the client event gate. An integration test runs real components together: ChatFlow's 32 tests drive the real Express app through supertest, or a real Socket.IO server through socket.io-client, against a real PostgreSQL 17, so they catch SQL, constraint, middleware-order and auth bugs a mock can't. An e2e test drives the deployed system like a user, usually through a browser; I don't have those. The pyramid says many units, fewer integrations, very few e2e, because cost and flakiness rise as you go up. I put the integration layer first in ChatFlow because almost all the risk was in the boundaries: validation, JWT, roles and rate limits.
A test passes locally and fails in CI. Walk me through it.
First I read the CI log for the actual assertion and timing, then sort it into four buckets. Timing: CI runners have fewer cores, so a timeout, a sleep or a rate-limit window behaves differently; I replace sleeps with waiting on the actual condition. Ordering: the test depends on state another test left, which shows up when the order changes; each ChatFlow file cleans the database in beforeAll and afterAll, and files run sequentially because they share one database. Environment: a variable, version or timezone differs; Vitest doesn't read .env, so CI must set everything explicitly, and I pin postgres:17 and Node 22. Resources: memory or file-descriptor limits. Then I reproduce locally with the same seed, order and versions, often by running the same container image.
Open vs closed load model. What is coordinated omission?
In a closed model a fixed number of virtual users each wait for a response before sending again, so throughput is an output: if the server stalls, the generator slows down with it. Coordinated omission is the result: during a two-second stall each user sends one late request instead of the many real users would have sent, so the stall shows up as one bad sample and the percentiles look better than reality. In an open model requests arrive on a schedule regardless of responses, like real traffic, and k6's arrival-rate executors do that. My ChatFlow fan-out test uses ramping-vus to hold sockets, but each socket emits on its own fixed timer and doesn't wait for the echo, so the send side behaves like an open model per connection. The REST throughput test is closed: 200 VUs with a 100 ms sleep.
Your resume says p95 40 ms at 1,000 sockets. How exactly did you measure that?
k6 opened 1,000 Socket.IO connections, each authenticated with a JWT in the handshake and auto-joined to its groups. Each socket emitted message:send every five seconds, about 200 messages per second, and each message carried its send timestamp in the content. The server validates with Zod, inserts into PostgreSQL and broadcasts to the room. Every receiving socket subtracted the embedded timestamp from its arrival time and recorded it in a k6 Trend, so the 40 ms is p95 over every delivery to every recipient, around 216 per message. p50 was 6 ms and p99 56 ms. The limits: k6 and the server ran on the same laptop, so there's no network latency, k6 competed for CPU, and 50 seeded users shared the sockets. It's a single-process baseline, not a production number.
State Little's Law and use it on something you built.
L equals lambda times W: the average number of items in a stable system is the arrival rate times the average time each spends inside. It needs no assumptions about distributions. ChatFlow's REST write test hit 961 requests per second with an average iteration of 137 ms, request plus 100 ms sleep. 961 × 0.137 ≈ 132, which is the time-weighted average number of VUs over that test's ramp, so the result is consistent. To size a database pool: at 300 queries per second taking 20 ms each, about six connections are busy on average, so a pool of ten gives headroom, and a pool of a hundred only moves the queue into PostgreSQL.
Why can't you average p95 across instances? What does histogram_quantile do?
A percentile isn't additive. If instance A serves 900 fast requests and B serves 100 slow ones, the fleet p95 depends on how all 1,000 samples sort together; the mean of A's and B's p95 weights them equally and gives a number that matches no real distribution. A Prometheus histogram stores cumulative bucket counters per instance, and counts do add. So you rate() each bucket, sum by (le) across instances, and histogram_quantile(0.95, ...) finds the bucket containing the 95th-percentile rank and interpolates linearly inside it. Accuracy depends on bucket edges, so you put edges near your SLO, for example 50, 100, 250 ms. A Summary computes quantiles in the client and can't be aggregated at all.
USE vs RED. What is saturation for a Node.js server?
USE is for resources: for each CPU, disk, pool or queue, check Utilization, Saturation and Errors. RED is for services: request Rate, Errors and Duration, ideally as a histogram. Saturation is work waiting because the resource is full. For Node the key resource is the single JavaScript thread, so saturation is event-loop delay: how late a timer fires, measurable with perf_hooks.monitorEventLoopDelay. CPU at 100% of one core tells you it's busy; event-loop delay tells you callers are queueing. ChatFlow's saturated run shows it: offered about 170k deliveries per second, the queue grew without bound, p95 went to 21.8 seconds and 8,323 messages were lost. Other saturation signals are the DB pool wait queue and Kafka consumer lag.
How would you trace one message end to end through Loom?
Today I can't; neither project has tracing, and I'd say that. I'd add OpenTelemetry. The Next.js route starts a root span when the run starts, and the event bus creates a child span for each persist and publish. The Redis Lua call becomes a client span. For Kafka I'd inject the W3C traceparent into the record headers, because propagation across a queue isn't automatic. The Go consumer extracts it and starts a span for process and the hub publish, linking it to the producer's span since one poll handles many records. Spans go to an OTel collector with tail sampling that keeps slow and error traces, then Jaeger or Tempo. I'd also put the trace id in every log line so logs and traces join.
What is Kafka consumer lag and how would you alert on it in Loom?
For each partition, lag is the log-end offset minus the consumer group's committed offset: how many records are written but not yet processed and committed. Count is hard to alert on because it depends on traffic, so I prefer time lag, the age of the oldest unconsumed record, and alert when it rises for several minutes. Loom's Go service commits manually after each poll and exports loom_last_event_timestamp_milliseconds, which gives freshness but not lag; with no runs it also looks stale. I'd export per-partition lag by asking the broker for end offsets and comparing with committed ones, or run an exporter like Burrow. In Loom lag grows if the poll loop blocks, which is exactly why the hub never blocks.
What happens when you run docker stop? Why does PID 1 matter?
Docker sends SIGTERM to PID 1 in the container's pid namespace, waits the grace period, ten seconds by default, then sends SIGKILL, which can't be caught. PID 1 is special: the kernel doesn't apply default signal actions to it, so a process without a SIGTERM handler simply ignores it and is killed ten seconds later with no cleanup. With shell-form CMD the shell is PID 1 and doesn't forward signals. ChatFlow uses exec form, so Node is PID 1 and its handler runs server.close(), disconnects Prisma and exits, with a 10-second force-exit. Loom's Go service uses signal.NotifyContext, closes the hub so WebSocket writers unwind, then calls server.Shutdown with a five-second deadline.
Inside Compose, why does localhost:5432 fail but postgres:5432 work?
Each container has its own network namespace, so localhost is the container's own loopback, and there's no Postgres there. Compose puts every service on a project bridge network and Docker runs an embedded DNS server at 127.0.0.11 that resolves service names to container IPs. That's why ChatFlow's Compose file sets DATABASE_URL to host postgres. ports: "5432:5432" only publishes the port to the host machine for your laptop's tools. Kafka adds a twist: the broker returns an advertised address and the client reconnects to it, so Loom defines an internal listener advertised as kafka:19092 and a host listener as localhost:9092. In GitHub Actions it's the reverse: steps run on the VM, so they use localhost.
You said the ceiling was the single-threaded broadcast. How do you know, and how would you confirm it?
The evidence is indirect. During the runs the server process sat at 90 to 110% CPU, one core, while the machine had idle cores. Connection count wasn't the limit, since 5,000 sockets were held at zero loss, and every run at or under about 97k deliveries per second stayed clean while 170k saturated. I didn't profile it, so I'd say "pointed to", not "proved". To confirm, I'd run the saturating case under clinic flame or node --cpu-prof and look for the hot frames: Socket.IO's broadcast, packet encoding, ws frame writes, JSON, versus Prisma and pg. I'd also check Postgres separately, because each message is a membership SELECT plus an INSERT, and run k6 on another machine so the generator isn't competing for the same CPU.

Loom drill-downs

L1. You say workers run in parallel. Node is single-threaded. Explain.
Concurrent, not parallel. Each worker mostly waits on a network call to the model provider. Promise.all starts every task in the current wave; while one waits, the event loop runs the others' callbacks. The work is I/O-bound, so one thread is enough; the computation happens on the provider's servers. Scheduling is Kahn's algorithm level by level: nextWave picks remaining tasks whose dependsOn are all complete. The cost is a barrier: a task waits for the slowest task in the previous wave even if its own dependency finished early. A ready-queue scheduler fixes that. CPU-bound work would need worker threads or separate processes.
L2. Why a Lua script and not MULTI/EXEC?
The write is read-then-decide: read the run's eventCount; if this sequence is already stored, return 0; otherwise update the hash, XADD with id {sequence}-0, refresh the TTL, return 1. MULTI/EXEC queues commands blindly and can't branch on a value read inside the transaction; WATCH gives optimistic retries. A Lua script runs atomically on Redis's single command thread, so no client sees the hash updated without the stream entry. The bus uses the return value to skip the Kafka publish for duplicates. Cost: a slow script blocks everyone, so it stays a handful of commands. Careful wording: the count check makes a repeat a no-op; an explicit XADD id that isn't greater than the last one throws an error.
L3. Can you find a hole in your own idempotency guarantee?
Yes. The script rejects old sequences but doesn't require the new one to be exactly eventCount + 1. If Redis is briefly down for event 40, the bus records the failure and continues; event 41 succeeds afterwards and the stream has a permanent hole at 40, while the run keeps spending model calls until it closes and is marked failed. Fix: require sequence == current + 1 in the script and stop the run on the first durability failure. A second, client-side one: when nothing is parked, the final replay stops after one page of 1,000 events, so a bigger gap can lose run.done. Fix: keep paging while a page comes back full.
L4. So it is exactly-once?
Exactly-once effect, not exactly-once delivery. Delivery is at-least-once: Kafka offsets are committed manually after processing, and the browser replays on any gap, so duplicates happen. Every consumer deduplicates by sequence: Redis ignores a sequence it already stored, and the browser's gate drops anything at or below lastApplied, applies exactly lastApplied + 1, and parks anything further ahead until a replay fills the gap. Order and uniqueness always hold under that invariant; completeness depends on the replay fetching everything. Exactly-once delivery over a network isn't possible in general, and the phrase invites a challenge.
L5. Why Kafka if Redis already has the events? Isn't it overkill?
Different jobs. Redis is the product's source of truth and serves replay to the browser. Kafka is a pipe to other services: the Go telemetry service consumes it without touching the web tier's Redis, and more consumers (analytics, audit) could subscribe without changing the web app. Records are keyed by run id, so one run's events land in one partition and stay ordered. Publishing is best effort by design: a Kafka failure never fails a run. At today's scale, honestly yes, it's overkill; one service could read Redis streams. I used it to decouple the telemetry service and to learn idempotent producers, keys and manual commits. Known cost: publishing is still on the serial delivery path, so a Kafka outage delays Redis writes.
L6. The WebSocket dies mid-run. What does the browser do?
The SSE response from the original POST has been open all along; its frames were read but not applied. On socket loss the browser flips a flag to apply SSE frames and triggers a replay, GET /api/swarm/{runId}?after=N, which reads the Redis stream with XRANGE from N exclusive. The gate drops the overlap. So switching is a flag flip, not a new request. Meanwhile the socket reconnects with exponential backoff, 500 ms doubling to 8 s with jitter, up to six consecutive failures. Jitter prevents a thundering herd when the Go service restarts. Weakness: if Kafka is down, the socket is open but silent and the UI looks frozen until a gap or run end; a liveness timer or server heartbeat fixes it.
L7. Walk me through the Go hub. Could it deadlock?
hub.go keeps a map of subscribers behind a mutex, each with a buffered channel of 256. publish locks, loops, and does select with default: send if there's room, otherwise remove the subscriber, close its channel and increment the dropped counter. Holding the lock while sending is safe only because the send can't block, so the lock is always released in bounded time; deadlock needs a lock held while waiting on something that can't happen. Release uses sync.Once because closing a closed channel panics. Counters are atomics so /metrics never takes the lock. Eviction beats dropping one event because it's loud: the client reconnects and replays from Redis. CI runs it under -race, including a test where one subscriber never reads.
L8. Who can connect to your telemetry WebSocket?
Not only logged-in users, and I'd raise this myself. CORS doesn't apply to WebSocket handshakes, so the Go service checks Origin against an allowlist, which stops other websites hijacking a visitor's browser. But a script that sends no Origin header gets through, the socket has no authentication, and the run-id filter is optional, so a script could subscribe to every run's events, including final documents. Fix: the Next.js server, which knows the session user, issues a short-lived signed token scoped to one run; the Go service verifies it on connect and requires the run id. The replay route is safe: it checks ownerId and returns 404, not 403, for other people's runs.
L9. How would you run three replicas of the Go service?
Today they would share one consumer group, so Kafka would split the six partitions between them. A browser connected to replica A would never see runs whose partition belongs to B. Options: give each replica its own consumer group so each sees every event, and accept that metrics are counted per replica, which sum across instances fixes for the dashboard; or route each browser to the replica that owns its run's partition; or put a pub/sub layer like Redis pub/sub behind the consumers. The first is simplest at this scale. Also note the nuance about rebalances: franz-go heartbeats from a background goroutine, so a stalled poll loop mainly stops commits and grows lag rather than forcing a rebalance as in the Java client.
L10. What's Loom's latency and throughput? How many users? (trap)
I haven't benchmarked Loom and it has no real users, so I won't quote numbers. Every number I quote is ChatFlow's, which I measured with k6. If I measured Loom, I'd use the timestamps already in each event envelope: time to first event, time per phase and total run time, as p50 and p95 across runs, plus Kafka-to-browser delay from the Go service. Most of a run is model latency, so system overhead would be small next to it. Likely follow-up: "I see Temporal in the repo." It's off the resume because the activity runs the whole swarm with maximumAttempts: 1; retrying would re-spend model calls and re-emit events. Making it real means one activity per phase with checkpoints and idempotency keys.

ChatFlow drill-downs

C1. Trace one message from emit to every recipient.
The socket authenticated at handshake: io.use verifies the JWT from handshake.auth.token and puts the user on socket.data. On connect the server reads the user's GroupMember rows and joins one room per group. message:send arrives; chat.handler.ts runs socketSendMessageSchema.safeParse, then the same sendMessage service REST uses: assertMembership (a SELECT, 403 if not a member) and a Prisma INSERT with sender and tags included. Then io.to(groupId).emit('message:new') writes to every socket in the room, sender included. Errors go back as an error event without internal messages. It's at-most-once to online sockets; offline users read history over REST with cursor pagination.
C2. How did you get ~97k deliveries per second, and what does zero loss mean?
1,500 sockets each sent every 5 seconds, so about 300 messages per second. Each message reached about 324 sockets: 50 users across 10 groups, with many sockets per user. 5.16 million receipts over the 53-second steady window is about 97k deliveries per second. k6's own rate says 54k because it averages over the ramp, so I quote the steady-state figure and say how I got it. "Zero loss" is k6's sio_messages_lost counter: every send's echo came back to its sender before the socket closed. I did not reconcile per-recipient counts against group membership, so I say "no lost messages" carefully. p95 at that load was 203 ms. Pushing to 400 msg/s × 433 recipients saturated the process.
C3. If 5,000 sockets were fine, what was the limit?
Total fan-out work per second, not connection count. An idle socket costs memory and a ping every 25 seconds. A delivery costs CPU on the one JavaScript thread: encoding the packet and writing a WebSocket frame per recipient socket. Every run at or below about 97k deliveries per second had zero loss; offering about 170k pushed the event loop past saturation, the queue grew, p95 reached 21.8 s and 8,323 messages were lost. The process sat at one core while others were idle. That's queueing theory: near 100% utilization, wait time blows up. Caveat: I inferred the thread from CPU, I didn't profile it, and k6 shared the machine.
C4. Scale ChatFlow to several Node processes.
Three things are in-process today. Broadcasts: io.to(room) reaches only this process's sockets, so add @socket.io/redis-adapter, which publishes each broadcast on Redis pub/sub so every process emits to its local members. Presence: onlineUsers is a Map, so move it to Redis with per-socket keys and TTLs. Rate limits: express-rate-limit's default store is memory per process, so use a Redis store. Behind the load balancer you need sticky sessions if clients can use HTTP long-polling, since its requests must hit the process holding the session; websocket-only clients don't. The database becomes the next limit: two queries per message on one Postgres. Nothing here is implemented; my numbers are one process.
C5. What does the typed event contract give you, and why still Zod?
types/socket.ts declares ServerToClientEvents and ClientToServerEvents, and the server is Server<ClientToServerEvents, ServerToClientEvents, InterServerEvents, SocketData>. Every emit and on is checked at compile time: a typo in an event name or a wrong payload field fails tsc, which CI runs. But types vanish at runtime. A client can send anything over the wire, so the handler still runs Zod on every payload, and REST routes use the same pattern through the validate middleware with 422 on failure. Types protect you from yourself; Zod protects you from clients.
C6. Why scrypt and timingSafeEqual?
Passwords are low-entropy, so the hash must be deliberately expensive to slow offline guessing after a leak. scrypt is memory-hard as well as CPU-hard, which makes GPU and ASIC attacks costlier than with plain iterated hashes. Each password gets a random salt so identical passwords hash differently and precomputed tables are useless. On login I re-derive the key with the stored salt and compare with crypto.timingSafeEqual, which takes the same time however many leading bytes match, so response timing doesn't leak how close a guess was. It throws if buffer lengths differ, so both sides must have the fixed key length. Login also returns 401 for both wrong password and unknown email.
C7. How do you authenticate sockets? What if the token expires mid-connection?
The client sends the JWT in the Socket.IO handshake auth payload, not the query string, so it doesn't end up in access logs. The io.use middleware verifies signature and expiry before any handler is registered; four tests in socket.test.ts cover valid, missing, invalid and malformed tokens. The weakness: verification happens once. A socket stays authenticated after its token expires, and removing a user from a group doesn't remove the socket from the room until it reconnects. Fixes: store the expiry on socket.data and disconnect at that time, have the client re-authenticate with a fresh token, and call socket.leave from the membership-removal path.
C8. Describe your rate limiting and its weaknesses.
Three express-rate-limit tiers per IP: global 100 requests per 15 minutes, auth 10 per 15 minutes counting only failures (skipSuccessfulRequests), and messages 30 per minute. Over the limit it returns 429 through the shared error handler with draft-8 RateLimit headers; ratelimit.test.ts checks the 31st message and the 11th failed login. Weaknesses: it's a fixed window in process memory, so it resets on restart and isn't shared across instances; IP-keyed limits punish users behind one NAT, and behind a proxy you need TRUST_PROXY or every user looks the same; and it guards REST only, so message:send over the socket isn't limited at all. Fix: a Redis token bucket keyed by user id, applied in the socket handler too.
C9. How are messages ordered, and what does the client do after a reconnect?
Messages are stored with createdAt and an index on (groupId, createdAt); history is newest-first with a cursor on the message id, and the second-page test checks the cursor chains. Live order is the order the single process finishes inserts and emits, which can differ from send order when two inserts race. There's no tiebreaker on equal timestamps and no per-group sequence number, so after a reconnect the client refetches history rather than asking for "everything after N". With several instances, clock skew makes createdAt worse. What I'd change, borrowing from Loom: a per-group monotonic sequence assigned at insert, clients ordering by it and requesting gaps, plus a client message id for dedup on retry.
C10. Tell me about your tests. Why not mock the database?
32 integration tests across six files: auth, validation, rooms, chat, socket and rate limiting. They build the real Express app with createApp() and call it through supertest, or start a real Socket.IO server on a random port, all against a real PostgreSQL. CI starts postgres:17 as a service container, gated on pg_isready, runs prisma migrate deploy, then Vitest. A mock would only prove I called the mock; the bugs I cared about were constraints, cascades, role checks and middleware order. Files run sequentially because they share a database and limiter state. The suite wipes every table, so setup.ts refuses any non-local host or a database name without "test": the app's .env points at a hosted database.

B1. Python and FastAPI (SoilSense / AgriPulse)

How it works internally

  1. uvicorn is an ASGI server. It runs one asyncio event loop per worker process, accepts connections, parses HTTP and calls your FastAPI app as await app(scope, receive, send).
  2. FastAPI matches the route, then resolves dependencies, path and query params and the body, validating them through Pydantic from your type hints. If validation fails it returns 422 before your code runs.
  3. An async def route runs on the event loop itself. A blocking call inside it, such as a synchronous HTTP client, time.sleep or heavy pandas work, freezes every other request in that worker.
  4. A plain def route is sent to a threadpool (AnyIO, 40 threads by default), so blocking I/O inside it is acceptable. Because of the GIL, only one thread runs Python bytecode at a time. Threads still help with I/O, since the GIL is released while waiting, but they don't help CPU-bound Python. For that you need more processes (uvicorn --workers N) or native code (numpy and pandas release the GIL in many operations).

In FastAPI, when should a route be async def and when plain def?

Use async def only when everything slow inside it is awaitable, such as an async DB driver, httpx.AsyncClient or an async SDK. The route then runs on the event loop and gives up control at each await, so one worker can handle thousands of concurrent waits. If the route calls anything blocking, such as requests, a sync SDK, or file or pandas work, use plain def. FastAPI runs those in a threadpool so the loop stays free. The worst case is an async def route with a blocking call inside, because it stalls every request on that worker. My webhook route does exactly that, and I'd change it.

What is the GIL, and does it make Python threads useless?

The Global Interpreter Lock is a mutex in CPython that lets only one thread run Python bytecode at a time. It exists because CPython's reference counting isn't thread-safe. Threads aren't useless: blocking I/O and many C extensions (numpy, pandas internals, hashing) release the GIL, so I/O-bound work overlaps well. CPU-bound pure-Python work doesn't speed up with threads. For that you use multiprocessing or several uvicorn workers, each with its own interpreter and GIL. Python 3.13 added an experimental free-threaded build without the GIL, but standard deployments still have it.

How is FastAPI different from Express?

Both are thin routing layers on top of a server. Express runs on Node's single JS thread with libuv underneath. FastAPI runs on asyncio under an ASGI server like uvicorn. The biggest practical difference is validation: FastAPI derives request validation and OpenAPI docs from type hints through Pydantic. In Express you add that yourself, which is what I did in ChatFlow with Zod middleware. FastAPI also has dependency injection built in, through Depends, for things like auth and DB sessions.

Operating systems

What are the four conditions for deadlock, and how do you prevent it?

Mutual exclusion, hold and wait, no preemption, and circular wait. All four must hold at once. Prevention breaks one of them. The most practical is circular wait: always take locks in a global order, for example by row id. You can also take all locks at once, or use try-lock with timeouts. Avoidance (Banker's algorithm) checks safe states before granting a resource. Detection builds a wait-for graph and kills a victim, which is what PostgreSQL does.

Explain paging and virtual memory. What is a page fault?

Each process sees its own virtual address space, divided into fixed-size pages (typically 4 KB). The MMU translates virtual pages to physical frames using page tables, with the TLB caching recent translations. A page fault happens when a page isn't in RAM. The kernel loads it from disk or swap (or allocates a zeroed page), updates the table and retries the instruction. Benefits: isolation, more address space than RAM, shared libraries, and copy-on-write fork. Thrashing is when the working set doesn't fit in RAM and the system spends its time paging.

Process vs thread, and what does a context switch cost?

A process has its own address space, file descriptor table and resources. Threads share their process's memory and fds but each has its own stack and registers. A context switch saves and restores registers, and between processes it also switches page tables, which can flush the TLB and costs cache warmth. That's why switching threads is cheaper than switching processes, and why user-space scheduling (goroutines, an event loop) is cheaper again.

Mutex vs semaphore vs condition variable.

A mutex allows one owner, and the owner must unlock it. A counting semaphore allows N concurrent holders and can be signalled by any thread, which suits limiting access to a pool of N connections. A condition variable lets a thread sleep until a condition becomes true, always used with a mutex in a while loop to handle spurious wakeups. The classic example is producer/consumer with a bounded buffer, using "not full" and "not empty" conditions.

CPU scheduling algorithms.

FCFS is simple but has the convoy effect. SJF/SRTF minimises average waiting time but needs burst estimates and can starve long jobs. Round robin uses a time quantum and gives good response time. Priority scheduling risks starvation, which aging fixes. Multilevel feedback queues use several queues with different quanta and demote CPU-heavy jobs. Linux's CFS, and EEVDF since 6.6, track each task's fair share of CPU time.

DBMS

1NF, 2NF, 3NF, BCNF with one example.

1NF: atomic values, no repeating groups. 2NF: 1NF plus no partial dependency of a non-key attribute on part of a composite key. 3NF: 2NF plus no transitive dependency (non-key depends on non-key). BCNF: every determinant is a candidate key. Example: storing (message_id, room_id, room_name) violates 3NF because room_name depends on room_id, not on the key. Move room_name to a Room table, as ChatFlow's Prisma schema does.

Clustered vs non-clustered index. Does PostgreSQL have clustered indexes?

A clustered index stores the table rows in index order (InnoDB's primary key is the table). A non-clustered index is a separate structure pointing to rows. PostgreSQL tables are heaps, and every index is secondary, pointing to a tuple id (ctid). The CLUSTER command reorders the table once but doesn't maintain the order afterwards. Index-only scans avoid the heap when the visibility map says the page is all-visible.

DELETE vs TRUNCATE vs DROP; WHERE vs HAVING.

DELETE removes rows one by one, fires triggers, can use WHERE and is fully logged. In Postgres it leaves dead tuples behind for VACUUM. TRUNCATE throws away the table's data files and is fast, with no per-row triggers; in Postgres it's transactional. DROP removes the table definition too. WHERE filters rows before grouping. HAVING filters groups after aggregation.

Computer networks

OSI vs TCP/IP layers, and where do HTTP, TLS, TCP, IP and Ethernet sit?

OSI has 7 layers: physical, data link, network, transport, session, presentation, application. TCP/IP has 4: link, internet, transport, application. Ethernet and MAC addressing sit at the link layer (L2), IP at network (L3), TCP and UDP at transport (L4), and HTTP at application (L7). TLS sits between TCP and HTTP and is usually described as session/presentation. That's why load balancers are called "L4" (route by IP and port) or "L7" (route by HTTP content).

What does ARP do, and what is a subnet mask?

ARP maps an IP address to a MAC address on the local network: "who has 10.0.0.5?" is broadcast, the owner replies with its MAC, and the answer is cached. A subnet mask (/24 = 255.255.255.0) splits an address into a network part and a host part. Hosts in the same subnet talk directly over L2. Traffic to anything else goes to the default gateway (router).

merge vs rebase?

Merge creates a merge commit joining two histories and keeps the true history. Rebase replays your commits on top of the new base, creating new commit hashes and a linear history. Don't rebase commits other people have already pulled. In upstream PRs (Oppia), you rebase your feature branch on the latest develop so the PR applies cleanly.

How do you find what's using port 3000 and why a process is slow?

ss -ltnp | grep 3000 (or lsof -i :3000) shows the listening socket and its PID. Then top/htop for CPU and memory, ss -s or ls /proc/PID/fd | wc -l for socket and fd counts, strace -p PID to see the syscalls it's blocked in, and dmesg for OOM kills. For Node, use --inspect or --cpu-prof. For Go, use pprof.

Design an LRU cache class with O(1) get and put.

Use a hash map from key to a node in a doubly linked list, with the list ordered by recency (head = most recent). get: look up the node, move it to the head, return it. put: if the key exists, update it and move it to the head; otherwise insert at the head, and if over capacity, remove the tail node and delete its key from the map. Both are O(1). For thread safety, a single mutex is simplest; under high contention you'd shard the cache by key hash. This is also how you'd explain Redis's allkeys-lru, except Redis uses approximate LRU by sampling a few keys, to save memory.
